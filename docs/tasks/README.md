# 任务卡与并行协作规则

> **文档职责**：规定任务卡的编号、内容、写入权限和生命周期，多个 agent 并行开发时的写入范围、
> 分支和合并规则，以及改变计划时的分级处理方式。
>
> **适用范围**：aTa 派发的任务都建任务卡；单 agent 任务预计跨会话、需要交接或与其他任务并行时也建卡。
> 能在一次对话内完成、且没有其他任务并行的小任务不必建卡。

## 1. 编号与命名

- 任务 ID 使用全局递增的 `T-###`，由 master 分配；下一个可用编号记录在 `docs/STATUS.md`。ID 与阶段号
  无关，阶段只作为卡片属性；已用 ID 不复用，任务取消后也不回收。
- 任务卡：`docs/tasks/T-###.md`；分支：`task/T-###-<英文短名>`；worktree：`../mica-wt/T-###`；
  提交信息前缀：`T-###:`。
- 返工沿用原 ID，在原卡片追加返工项；只有范围变化大到需要独立验收时才新开 ID。

## 2. 生命周期

| 状态 | 进入条件 | 更新者 |
|---|---|---|
| 待开始 | master 创建卡片并登记到 STATUS | master |
| 进行中 | 执行者开始工作 | 执行者 |
| 阻塞 | 缺少决策、授权或前置任务 | 执行者记录原因，master 同步 STATUS |
| 待验收 | 执行者完成并提交报告 | 执行者 |
| 已验收 | master 审查通过并完成收口 | master |
| 挂起 | 计划变更中暂停（§6.1），卡片写明恢复条件 | master |
| 已取消 | 计划变更中放弃（§6.1），随后删除卡片 | master |

派发时，master 创建任务卡并在对话中告诉执行者卡片路径；对话里的任务单只作为摘要，内容以卡片为准。

验收收口时，master 依次完成：合并任务分支并按 `docs/code_spec.md` §2.4 复验 → 落地「文档变更建议」
→ 把「候选经验」转入 `docs/lessons/inbox.md` → 更新 STATUS → 删除任务卡、worktree 和任务分支。卡片删除
后用 Git 历史追溯。

## 3. 写入权限

- **master**：头部字段、目标、必读、写入范围、契约与约束、验收。范围调整时同步告知执行者。
- **执行者**：只追加「进展与交接」「候选经验」「文档变更建议」，以及返工时的处理说明；不修改 master
  编写的小节。发现范围不足或计划与代码现实冲突时，记录到「进展与交接」并停下报告。
- **进展记录**：执行者在每个里程碑、会话结束或上下文压缩前追加 1～3 行（已完成 / 下一步 / 注意事项），
  使新会话读卡即可接续；只记录真实完成的部分，不预写结果。

## 4. 卡片模板

```markdown
# T-### <任务标题>

状态：待开始 · 阶段：<阶段或治理期> · 负责：<执行者> · 分支：task/T-###-<slug> · 基线：<commit>
依赖：<前置任务 ID 或无> · 提交授权：<是：仅限任务分支 / 否：交付未提交改动>

## 目标
<一个可以独立验收的闭环，写清完成后可以观察到什么>

## 必读
- <文档或源码，精确到章节或文件>

## 写入范围
允许：
- <文件或目录>
禁止：
- <不能修改的文件；并行时列出其他任务占用的热点文件>

## 契约与约束
- <必须保持的公共行为、跨模块契约和状态所有者>

## 验收
- 验证级别：`docs/code_spec.md` §2.4 中的「<实际改动>」
- <任务特有的验收点>

## 进展与交接
<!-- 执行者追加：日期 · 已完成 / 下一步 / 注意事项 -->

## 候选经验
<!-- 可复用的教训：现象、证据位置、建议去向 -->

## 文档变更建议
<!-- 需要 master 落地的规格、计划或治理文档修改 -->
```

## 5. 并行协作

### 5.1 派发前（master）

1. **契约先行**：多个任务共同依赖的契约变更单独成卡，先完成合并，再派发依赖它的任务。
2. **范围不重叠**：对照 STATUS 中进行中任务的写入范围；任意两张进行中卡片的允许写入范围不得重叠。
3. **热点文件独占**：以下文件被多数模块或所有任务共享，同一时间只允许一张进行中卡片修改：
   - 依赖与打包：`pyproject.toml`、`uv.lock`；
   - 公共导出：`src/mica_agent/__init__.py`、`tests/test_public_api.py`；
   - 共享契约：`models.py`、`events.py`、`interactions.py`、`cancellation.py`、`tool_contracts.py`、
     `tool_presentation.py`、`checkpoint_contracts.py`、`session_contracts.py`、`providers/base.py`；
   - 共享测试资产：`tests/sse_transport_helpers.py`、`tests/test_distribution.py`；
   - 治理文档：`AGENTS.md`、`docs/STATUS.md`、`docs/PROJECT_PLAN.md`、`docs/decisions.md`、
     `docs/code_spec.md`。
4. **登记依赖**：前置关系写进卡片的「依赖」字段，并在 STATUS 中体现。

### 5.2 执行中（执行者）

- 在自己的 worktree 和任务分支上工作：`git worktree add ../mica-wt/T-### -b task/T-###-<slug>`。每个
  worktree 使用独立的 `.venv`，首次使用前执行 `uv sync --python 3.11`。
- 只修改卡片声明的范围；需要修改范围外文件时停下，记录并报告 master。
- 卡片授权提交时，只在自己的任务分支提交；任何情况下都不合并、不推送、不改写他人分支。
- `docs/module_map.md` 只修改自己写入范围内文件的词条，与对应源码职责变化同步。

### 5.3 合并（master）

- 按依赖顺序逐个合并到 `main`；每合并一个任务，就在 `main` 上按该卡片的验证级别复验。
- 出现冲突或复验失败时退回执行者：基于最新 `main` 更新任务分支后重新验证。
- 推送远端只在用户要求时进行。

单 agent 且没有并行任务时，可以直接在当前工作区工作，不强制使用 worktree。

## 6. 计划变更

改主意、调整范围和中断计划都是正常路径。按影响分级，只做该级别要求的最少动作；拿不准级别
时按高一级处理。单 agent 模式下由该 agent 承担 master 的动作；L2、L3 必须先经用户确认。

| 级别 | 典型情况 | 最少动作 |
|---|---|---|
| L0 微调 | 实现细节或文案变化，不改变目标、范围、契约和验收 | 直接执行；执行者在「进展与交接」记一句 |
| L1 任务变更 | 增减需求，调整写入范围、契约或验收 | master 修改卡片对应小节，在「进展与交接」记下变更与原因并告知执行者；影响其他进行中任务时一并调整 |
| L2 推翻已确认内容 | 改变 `docs/decisions.md` 中的决定、`docs/PROJECT_PLAN.md` §4 的约束、需求简报的「已确认」条目或已验收的产品行为 | 用户确认后，在 decisions 追加取代旧条目的新决定 → 更新该事实的唯一归属文档 → 逐一处理受影响的卡片和文档 |
| L3 主线切换 | 暂停当前阶段或主线，转做另一项工作 | 按 §6.1 |

### 6.1 主线切换

1. 停止在原主线上派发新任务。
2. 逐张收敛进行中的任务卡，三选一：
   - **收尾**：做到可以独立验收的点，按 §2 收口；
   - **挂起**：执行者补全「进展与交接」，master 在卡片写明恢复条件，保留卡片、分支和 worktree；
   - **取消**：master 在 STATUS 记下原因后删除卡片、worktree 和分支；有价值的结论转入 decisions
     或 inbox。
3. master 在 STATUS「暂停的主线」记录断点：基线 commit、已完成与未完成的部分、挂起的任务和恢复条件。
4. 新主线要有入口：一条经用户确认的决定，加一份写明生命周期的计划；小型主线可以直接用任务卡。
5. 恢复原主线前，master 对照暂停期间新增的决定和规范重审挂起的卡片，修订后再派发。暂停的阶段
   不标为已完成，取消的任务不写成已验收。

### 6.2 探索性试验（spike）

还不确定要不要做、想先试试时，用 spike 回答问题，而不是直接进入交付：

- 在 `spike/<英文短名>` 分支或独立 worktree 上进行，不建任务卡，不修改长期文档；跨会话时在 STATUS
  「进行中任务」登记一行。
- 结束时由 master 记录一句结论：采纳则按 L1 或 L2 转成正式任务，放弃则在 STATUS 写明原因。
- spike 代码默认不合并；需要保留时，按正常任务的写入范围、规范和验收重新走一遍。
