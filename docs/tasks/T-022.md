## 做法与约束

- **职责分离**：命令入口统一识别、可用性和分派；菜单只管筛选、选中项、确认和呈现；App 协调配置、会话和连接，Runtime 管唯一 Run。TUI 不读 Key、不写 JSON、不改 App/Engine 私有字段。后续命令复用入口，不预建它们的 handler 或空菜单。
- **菜单与选择**：遵守规格键位；名称和供应商筛选，同模型不同供应商仍是不同项。Enter 保存当前会话选择、安装成功后关闭；Ctrl+S 只保存全局默认，不切换当前、不关闭菜单、不改工作区覆盖；CAS 冲突或保存失败不显示假成功。目标不支持的协议不可安装，不能偷偷降为 Chat Completions。
- **确认与容量**：跨供应商说明后续请求会发送可用历史与指引；目标容量缩小时先确认。沿用 R5 的粗估范围、公式、来源和超限处理；不删历史、不压缩、不用确认绕过已知限制。切换不重新加载系统指引、不重注册工具或执行旧工具。
- **保存与安装**：候选 Provider/Engine/运行绑定先准备；锁内原子保存选择与安装之间无 await、用户回调或可取消线程写入。准备/保存失败保留旧运行与磁盘选择并收口候选；安装后清理/渲染失败与“切换未成功”分开报告。
- **资源收口**：沿用 R5 的单次关闭与所有权要求，明确操作 task、取消和 App 关闭关系；有界等待不是假装资源已释放，不盲目重试或吞错。下一 Run 仍走 A1 `prepare_run`，实际请求使用新模型、预算、能力和供应商凭据。
- **输入与草稿**：复用唯一终端消费者；命令候选与可编辑 composer 共存，进入 `/model` 后功能菜单才取代整个底部输入/事实/状态区，关闭恢复草稿、物理光标和事实。运行中只允许本地草稿，不把普通 Enter 变成排队 Run；Ask/Permission 独占输入，不弹命令候选或抢回答。忙时已识别本地命令灰色短暂提示，不送模型、不取消、不排队；未匹配内容遵守普通消息提交边界。
- **测试体量**：先做代表性可运行闭环，不逐字段/私有方法堆测试；替身仅隔离网络、时钟和终端。复用 A1 配置/会话/VT 资产，旧预期改变时同步校正并交代独有保护，不保留互相矛盾的测试。

## 第一关方案 · 2026-10-04 · A2 编码前定向交回

本节只描述施工方案，不表示源码已经修改或产品已经验收。方案以当前 A1 实际接缝为准：`MicaApp` 已持有当前 Provider、`ConnectionBinding`、`ConfigService`、`SessionService` 和单一 `_engine`，`MainBufferRuntime` 是唯一 Run 消费者，`MainBufferScreen` 是终端输入模式机；不依赖 T-021 中尚未实现的旧方法。

### 1. 统一命令路径

新增最小的 `tui/main_buffer/commands.py` 静态登记表。每个登记项只包含命令名、参数规则、已交付状态和 handler 标识，不开放插件注册、动态导入或未交付命令的空 handler。本轮登记项只有 `model`，其 handler 由 Screen 交给菜单/App 协调；`login`、`settings`、`reload`、`help` 等不登记为可用，也不制造假成功动作。

所有提交都经过同一条路径：`ComposerEditor.submit_text()` 取得完整原文 → 命令识别器按完整文本判断 → 登记表查找并执行统一可用性判断 → 分派到命令动作或 Runtime。Screen 不再让普通 `_submit()` 直接绕过命令层。命令动作不创建 user row、不调用 `Runtime.submit()`，普通消息才进入 A1 的 `prepare_run`/消费链。

本轮语法取舍如下：

- 只有去除首尾空白后完全等于 `/model` 的单行文本才是可用命令；`/model` 后带任何参数都给固定参数诊断，不作为普通消息发送，也不打开菜单。这样不会把拼写错误静默发送给模型。
- 以 `/` 开头的单行未知名称给固定“命令尚未交付/未知命令”诊断；不把 `/login` 等显示为可用，不执行配置写入或网络动作。空白提交仍按现有规则清空，不生成记录。
- 含换行的提交一律是普通消息，即使第一行是 `/model`；多行内容通过同一个编辑器提交路径进入 Runtime，避免截断用户原文。单行粘贴的 `/model` 与手打命令相同；多行粘贴保留完整内容并按普通消息处理，长粘贴仍由编辑器的原文展开机制保证不丢数据。
- 识别只使用安全的命令名/参数形状，不把未清洗的输入或异常文本拼进诊断。菜单开启后由菜单独占按键，命令识别器不二次消费方向键、Enter、Ctrl+S、Esc。

统一可用性判断至少检查：命令已登记、Screen 未处于 `ask`/`permission`/`closed`、无菜单或重配操作、App 未关闭；`/model` 打开前还须满足实际空闲。未通过时只产生本地固定诊断或忙时提示，绝不排队、取消当前 Run、送模型或创建第二 Run。

### 2. 真实输入与空闲边界

当前 `_handle_key()` 在 `running` 直接返回，导致忙时 Enter 不可能到达命令处理。施工时保留 Ask/Permission 的最前优先级和现有 Escape/Ctrl+C 取消语义，但允许 running 状态的文本、粘贴、换行和编辑继续写入本地 composer 草稿；running 状态的 Enter 只调用统一提交路径。若草稿是完整命令，立即显示短暂灰色忙时提醒（命令未执行），保留草稿，不调用 Runtime；若是普通消息，也只显示忙时提醒并保留草稿。这样完整命令在忙时真实可达，同时不会把 Enter 变成排队请求。普通输入不会改变当前 Run。

`ask` 和 `permission` 分支仍先于命令层，所有输入交给现有交互对象；菜单不会在这两个模式中打开，也不抢回答/权限输入。`CLOSED` 和 shutdown 中的输入统一拒绝。菜单打开后 Screen 将整个底部输入、事实和状态区交给菜单消费者，编辑器草稿暂存但不处理为命令。

“空闲”不由最后一个 `RunCompleted`/`RunFailed`/`RunCancelled` 事件单独决定。打开菜单和执行 Enter 切换前，必须通过 Runtime 的公开 `wait_idle()` 等待/确认消费 task 已结束并已 release，再检查 `app.is_busy`、关闭状态和没有重配 task。若调用点本身处于 running、Ask、Permission、重配或关闭中，则立即拒绝并给忙时提示，不等待 Run 结束后再自动执行被拒命令。终态事件只更新显示；在 Runtime `_release` 尚未完成时仍按忙处理。

Screen 的命令/菜单操作使用独立的本地 asyncio task，以便目录准备、确认和候选关闭不阻塞输入、刷新或退出。任务持有代际标识；菜单关闭、更换筛选或 Screen 关闭后，迟到结果只能被丢弃，不能恢复菜单或改写当前事实区。

### 3. 业务入口、预览、保存与安装

不在 Screen 读取 Key、URL、JSON 或 Provider 私有字段。`ConfigService` 增加只读的模型选项投影/目标解析接缝，复用已有 `ConfigSnapshot.providers`、`ModelConfig`、`ConnectionBinding` 和 `resolve()`；返回给 TUI 的不可变快照只含 provider/model ID、清洗后的显示名、协议、能力来源、可用状态、当前标记和默认标记，不含 URL、Key 或异常原文。保存默认仍调用现有 `ConfigService.save_default_model()`，由 `ConfigStore.save_default_model()` 锁内重读、CAS 比较、保留无关字段并原子替换。

`MicaApp` 增加 A2 的公开协调接缝，Screen 只传 `SessionSelection` 和用户确认结果：

- `preview_selection(target)` 只读检查目标是否来自本地可用目录或当前临时连接、协议是否为已交付的 `openai-completions`、凭据来源是否可用、当前/目标能力和切换确认理由。跨供应商时固定说明“后续请求会把可用历史与指引发送到目标渠道”；目标明确 `contextWindow` 小于当前估算占用时要求确认，不假称只发新一句话。
- 估算复用同一内部函数，范围含冻结 system/AGENTS、`SessionService.context_snapshot()`（含 checkpoint 重编码）、待提交 prompt（菜单预览时为空）、工具 schema、消息角色、工具调用 ID 和参数 JSON；公式沿 R5 为 `ceil(total_utf8_bytes / 3) + 16 * message_count + 256`，再加冻结输出预算，并显示容量/来源。它是带来源的粗略风险提示，不是实测 token，也不把粗估直接当成确定超限；明确容量与输出预算自身冲突仍拒绝，服务端真实超限照常失败，不删历史、不压缩、不用确认绕过硬冲突。
- `reconfigure(target, confirmation)` 由 App 负责候选 Provider、候选 Engine 和新运行绑定准备。CLI 现有 `ProviderFactory` 通过同一装配路径注入 App；候选使用解析出的 `ConnectionBinding`，建立真实 `AgentEngine`，复用现有 `ToolExecutor`/`InteractionBroker` 接缝和当前 context/session，不重建 system prompt、不注册第二套工具、不执行历史工具。候选准备完成前不改当前 Provider、Engine、会话选择或事实区。
- Enter 当前选择的事务顺序为：确认状态和旧选择仍匹配 → 候选与新绑定已完整准备 → 同步调用最小新增 `SessionService.update_selection(session_id, selection)`（内部复用 `JsonlSessionStore.update()`，只重建 v5 meta 的 `selection`/时间字段，原样保留 entries、Turn、checkpoint、工具事实和 wire）→ 同一无 `await`、无用户回调、无可取消线程写入的区间安装新绑定 → 从已安装绑定更新安全事实快照 → 关闭菜单。保存失败则不安装并关闭候选；安装后一次渲染失败单独报告“选择已生效，界面更新失败”，不反向写旧选择。
- Ctrl+S 只调用 `ConfigService.save_default_model(highlighted, expected_default_at_open)`，不改变当前会话选择、当前 Provider/Engine、工作区覆盖，也不关闭菜单。临时 `mica-env:`/`mica-direct:` 目标按现有规则拒绝保存全局默认并显示固定原因。CAS 冲突要求重新加载/确认，不能显示假成功。Esc 只关闭菜单并恢复草稿、光标、事实区。

因此会话当前选择与全局默认始终独立：Enter 成功后后续 Run 使用新绑定并持久化本会话 selection；Ctrl+S 成功只改变全局 config default；正常/中断/工具 checkpoint 提交不会隐式改写启动时的 CLI 临时覆盖或会话元数据。新会话、恢复会话、未配置 App 和临时 CLI 连接均通过同一个选项投影：未配置时可以查看本地可用目录但不能伪造可用当前连接；恢复的 saved selection 仍优先；临时 CLI 连接显示为当前候选/当前选择但不可成为持久化全局默认。

### 4. 取消、资源所有权和退出

候选准备、菜单筛选/读取和重配协调都绑定 App/Screen 的操作 task。Esc 在菜单中取消菜单操作并关闭候选，Ctrl+C 遵循现有双击退出边界：首次取消菜单/等待，第二次请求退出；关闭或退出会取消尚未提交的菜单任务。外层取消不直接杀掉已进入保存/安装边界的 App 重配 task；App 先标记 closing，等待该操作返回确定结果后再关闭已安装资源。

资源状态和所有者按阶段保持明确：

- 准备前只有当前连接由 App 所有；预览不创建 Provider。候选创建后立即由 App 的当前重配操作持有，准备失败、用户取消或菜单关闭都由创建者关闭一次并保留关闭任务/结果。
- 保存前失败保留旧磁盘选择、旧 Provider、旧 Engine 和旧事实区；候选不得泄漏。保存成功后的同步安装区间不可被取消打断，磁盘与内存最终都进入新选择，不出现“磁盘新、运行旧”的正常路径。
- 安装后旧 Provider 进入 App 持有的退休记录；每个对象最多创建一次 `aclose` task，记录 pending/closed/failed，不丢引用、不盲目重试。旧连接关闭失败或有界等待超时只报告“选择已保存，旧连接未确认关闭”，不回滚新选择、不谎称资源已释放；未完成的 task 继续由 App 持有。
- 若仍有退休清理未完成，下一次重配按既定边界拒绝或等待正在进行的单次清理，避免无限累积；当前新 Provider 仍只允许 A1 的唯一 Runtime 发起下一 Run。App 关闭时先禁止新动作，等待活动 Run/重配跨过可确定边界，再对当前、候选和退休资源执行已记录的单次收口；最终未确认状态交给 Screen/CLI 的安全诊断。
- 任何阶段不启动第二个 Run 消费者；`MainBufferRuntime` 仍是唯一拥有 CancellationToken、consumer task、真实 run_id 和 `MicaApp.run()` 流的组件。重配不改变 Engine/Provider 公共契约，也不在 Runtime 里另建连接所有权。

## 第一关复审与返工 1 补充 · 2026-10-04

本节只补五项技术边界和候选输入链路，不改写前文历史方案，不表示任何接口已经实现或已经验证。命令识别的产品取舍仍等待用户确认；以下把可复用的输入机制与待确认分支分开，未获确认前不把任一分支写入源码。

### 1. 候选呈现、编辑和提交链路

`ComposerEditor` 继续是唯一草稿和光标所有者。每次插入、删除、粘贴、换行或光标相关文本变化后，Screen 将完整草稿交给统一命令登记表做一次纯函数筛选：只有单行、去除首部空白后以 `/` 开头的草稿进入候选计算；多行、去掉 `/` 或 Ask/Permission/功能菜单/closed 模式直接没有候选。候选项只来自同一登记表中 `implemented=True` 的命令，本轮只有 `/model` 具备候选和动作，不显示 `/login`、`/settings`、`/reload` 或其他未交付命令。

候选列表与 composer 同时呈现，不改写草稿，不创建第二输入消费者。继续输入只更新筛选词和高亮；↑/↓ 只移动高亮；Space、普通字符、退格和粘贴仍由编辑器处理。候选状态保存其打开代次、筛选文本和高亮索引，避免迟到异步结果覆盖新草稿。Esc 只关闭候选并保留原文、光标和编辑模式，不自动执行；关闭后再次 Enter 仍重新走同一提交入口。

Enter 必须先取得提交时的完整原文，再进行一次统一分派：空白按现有空提交规则处理；匹配到已实现命令且满足最终产品确认的精确匹配规则，才进入本地 handler；否则原文完整交给普通消息路径。这里必须由用户确认以下取舍后才能编码：

- **候选回退方案**：`/`、`/mo` 等有候选时，Enter 只有在高亮项与完整规范化草稿匹配时执行；存在未知名称、额外文字或参数时不执行本地动作，完整原文作为普通消息发送。该方案不吞掉 `/model` 后的余文。
- **严格诊断方案**：对已登记命令带参数或未知名称给固定本地诊断，不发送模型；这保留前文原始方案的安全拦截语义，但不符合当前 D-024 需求修订所描述的原文回退方向。

在用户确认前，`commands.py` 只实现可测试的登记、候选筛选和不带副作用的解析结果，不实现上述分支的最终提交动作。无匹配（包括单独 `/` 和 `/unknown`）不能因默认高亮执行命令；多行和多行粘贴完整保留并按普通消息候选规则处理。单行粘贴与手打输入使用同一文本变化和提交路径，不截断、不改写、不丢弃余文。

### 2. 容量、确认快照与空闲准入

容量规则按 R5 校正为两条互不替代的判断。目标 `contextWindow` 小于当前估算占用时，无论估算是否已经超过目标，都必须显示目标容量和来源并要求用户确认；确认不能解除已知硬冲突。粗估总量超过明确容量时，直接阻止新请求和切换后的请求，不删历史、不压缩、不靠确认绕过；程序默认容量只作风险提示，不冒充服务端确定拒绝。`preview_selection()` 与候选准备/`prepare_run()` 共用同一带来源的纯估算函数，覆盖冻结指引、会话上下文（含 checkpoint 重编码）、工具 schema、角色、工具调用 ID/参数和固定输出预算，仍使用 `ceil(total_utf8_bytes / 3) + 16 * message_count + 256`，并明确这是粗估而非 tokenizer 结论。

空闲准入不调用会等待的 `wait_idle()` 作为第一步。统一命令或菜单动作先在当前事件循环内同步检查：Screen 模式及关闭标志、菜单操作是否存在、`Runtime.is_closed`、`Runtime.active_task`、App 的 active run/reservation、重配操作状态和 App closing 状态。任一项显示忙、关闭或已有操作，就立即拒绝并显示固定短暂提示；不得等待本次 Run 结束后自动执行被拒命令。若所有检查均为空闲，App 在第一次可能 `await` 之前同步取得重配 reservation/operation generation，然后才创建候选准备 task；该 reservation 使后续普通提交无法再接纳第二个 Run。仅在已取得 reservation 且操作边界需要确认收口时，才允许对已知 task 做必要的 `wait_idle()`/复核。

`RunCompleted`、`RunFailed` 或 `RunCancelled` 到达只代表显示可更新，不代表 Runtime consumer 已通过 `_release` 释放，也不代表 App reservation 已清空；只要 `active_task` 或 reservation 仍存在，命令仍按忙处理。菜单准备期间仍由同一个终端循环处理 Esc、首次 Ctrl+C 和退出，不阻塞键盘或刷新。

### 3. 选择确认、会话保存与安装

拟新增的最小公开输入/结果采用不可变快照，而不是向 Screen 暴露配置或连接私有对象：`SelectionTargetSnapshot` 含稳定 provider/model 标识、清洗后的显示名、协议、能力及来源；`SelectionPreview` 绑定菜单打开代次、当前会话 selection、目标快照、当前/默认标记、估算和确认理由；`ReconfigureResult` 只返回 committed/cancelled/rejected/cleanup-unconfirmed 等安全状态和安全诊断。快照不含 URL、Key、异常原文或可恢复性不明的临时内部引用。

Enter 在确认窗口和真正提交前重新核对菜单代次、当前运行 selection、目标快照身份、App reservation 以及磁盘预期 selection。`SessionService.update_selection(session_id, selection, expected_selection=...)` 是最小业务入口；它必须让 `JsonlSessionStore` 在既有进程/文件锁内重读当前 meta，比较 `expected_selection`，只在相等时原子更新 selection 和更新时间，原样保留 v5 entries、Turn、checkpoint、工具事实和 wire。锁外快照只能用于提前提示，不能用来覆盖另一窗口的更新；冲突返回拒绝并保留旧运行、旧磁盘选择和菜单草稿。

事务顺序保持为：候选 Provider/Engine/绑定准备完成 → 重新确认容量与 selection 快照 → 会话更新在锁内成功 → 无 `await`、无用户回调、无可取消线程写入地安装新绑定 → 从 App 真实安装结果生成安全事实 → 关闭菜单。保存或准备失败不安装候选。Ctrl+S 继续独立走全局默认 CAS，不改变当前会话、Provider、Engine 或工作区 selection。

临时 CLI 连接能否由 Enter 写入会话 selection 是新增产品边界，不能由 worker 默定：需要用户在“临时目标只可查看/切换但不持久化”与“允许保存可稳定重建的临时目标”之间确认。实现必须至少拒绝把仅含进程内 URL/Key 的不可恢复引用写入会话；在该取舍确认前，临时行可展示当前标记和预览，但持久化动作返回明确拒绝。初始未配置、恢复 selection、普通/工具历史和 CLI 临时覆盖都继续通过同一 ConfigService/SessionService 装配边界进入投影，不复制配置读取或冻结指引；启动时的 CLI 临时覆盖不由普通 Run 写回。

### 4. 取消、迟到结果与资源结束

候选准备和重配操作使用 App 持有的 operation token 与代次。保存前收到菜单 Esc、首次 Ctrl+C 或退出：向 App 操作传达取消，候选 task 结束或进入有界取消路径，候选 Provider/Engine 由创建者关闭一次，旧 Provider、旧 Engine、旧会话 selection 和事实保持不变。不能只取消 Screen 外层的 `shield` 等待而让 App 操作继续无记录地改状态。

会话保存成功是不可逆提交点。保存后收到取消，不恢复旧 selection，不吞掉已提交结果；App 必须继续同步安装新绑定、更新真实事实，或因 Screen 退出转入 App closing。安装完成后旧 Provider 进入 App 的退休资源记录，新选择保持有效；旧资源关闭失败/超时只产生“选择已保存，旧连接未确认关闭”的安全报告，不回滚新状态。迟到的候选预览只能按菜单代次丢弃；已提交的选择、运行绑定和关闭结果属于 App 事实，不能用代次逻辑丢弃或重新套用旧事实。

资源状态分为 `candidate`、`current`、`retiring-pending`、`retiring-closed`、`retiring-failed`，所有者始终是 App，创建者登记引用；同一对象只允许登记一个 close task。`retiring-pending` 未完成时，后续重配立即拒绝且不排队；`retiring-failed` 表示关闭未确认，同样阻止后续重配，不盲目重试，不用丢引用解除阻塞。失败原因只映射为固定安全诊断，引用和 task 记录继续由 App 持有。

App 退出先标记 closing，拒绝新命令、Run 和重配；取消尚未提交的操作并等待其确定到保存前取消或保存后安装完成，等待受明确 timeout 限制。随后对当前、候选和退休资源复用已登记的单次 close task，在独立有界等待内收口；task 超时保留引用并报告未确认，不以 `shield` 无限等待、不重复 `aclose`、不靠垃圾回收宣称释放。沿用 A1 `MainBufferRuntime.aclose()` 的可见 cleanup error 保护，Screen 只显示固定安全状态。
