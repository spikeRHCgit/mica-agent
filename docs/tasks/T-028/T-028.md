## 具体实现目标

- 新写入的会话为 v6；v1～v5 会话读取时不改动文件字节，续接全部为空；第一次业务写入时整文件升级到 v6，写入失败时原文件字节不变，之后可以重试。
- 完成的轮次为每条 assistant 消息（中间步骤和最终回答）各保留一个续接位置，可以为空；中断检查点的每个进度步骤可以带一条续接；部分回答不带续接。
- 构造轮次和检查点时，续接先经过清洗判定，再检查与对应 assistant 消息的关联；关联不符、单轮合计超过 1 MiB 时拒绝构造。
- v6 读取时，续接数量与 assistant 消息不对应、续接违反契约、关联不符、超过单轮上限，都按会话格式错误拒绝，错误信息不带续接内容。
- 续接内容不出现在轮次、检查点、进度步骤的 repr 中。

## 具体实现方案

**版本**：`CURRENT_SESSION_FORMAT_VERSION = 6`，支持集合为 1～6。`SessionMeta` 的 v6 与 v5 字段相同；`selection` 的版本条件由「等于 5」改为「至少为 5」，元数据解析中允许 selection 的分支同样覆盖 v6。

**`TurnEntry`**（`session_contracts.py`）：

- 新增最后一个字段 `continuations: tuple[ModelStepContinuation | None, ...] = field(default=(), repr=False)`。
- `__post_init__` 中，在现有的中间消息清洗之前：
  1. 按 `context_messages` 的顺序取出全部 assistant 消息（中间步骤的 assistant 消息和最终回答），记为 `assistant_messages`；
  2. `continuations` 为空元组时，规范化为与 `assistant_messages` 等长、全部为 `None` 的元组；不为空时必须是 tuple，长度必须相等，否则抛 `ValueError`；元素必须是 `ModelStepContinuation` 或 `None`，否则抛 `TypeError`；
  3. 每个非空记录先调用 `sanitize_step_continuation(record, message)`，再调用 `check_step_association(cleaned, message)`，结果写回；
  4. 非空记录的 `continuation_size` 合计超过 `MAX_TURN_CONTINUATION_BYTES` 时抛 `ValueError`。这里不自动降级，降级由提交方调用 `apply_turn_size_limit` 完成。
- `context_messages` 不变。

**`RunCheckpointProgress`**（`checkpoint_contracts.py`）：

- 新增最后一个字段 `continuation: ModelStepContinuation | None = field(default=None, repr=False)`。
- 非空时，把这一步还原成一条 assistant 消息：正文取 `assistant_message.content`，没有正文时为空串；工具调用依次取 `tools` 各项的 `call`。然后依次调用 `sanitize_step_continuation` 和 `check_step_association`，结果写回。

**`RunCheckpoint`**：全部进度步骤中非空续接的 `continuation_size` 合计超过上限时，抛 `ValueError`。

**导入**：`checkpoint_contracts.py`、`session_contracts.py` 从 `continuation_contracts` 和 `message_sanitizer` 导入所需符号；`continuation_contracts` 不导入这两个模块，不产生循环导入。

**wire**（`serialize_session_record` 只输出 v6）：

- `turn` v6 的字段为 v3～v5 的字段加 `continuations`。它是数组，长度等于 `messages` 中 assistant 消息的条数，元素为 `serialize_continuation` 的结果或 `null`。
- `run_checkpoint` v6 的 `progress` 元素字段为 `assistant_message`、`tools`、`continuation`；`continuation` 为续接记录或 `null`。`_parse_checkpoint` 允许的版本改为 4、5、6。v4、v5 的 progress 元素仍然只能有 `assistant_message`、`tools` 两个字段，不能出现 `continuation`；v6 的 progress 元素必须有这三个字段。
- 读取：
  - v3～v5 的 `turn` 必须恰好是原有字段，出现 `continuations` 按多余字段拒绝；
  - v6 的 `turn` 必须带 `continuations`；
  - 续接用 `parse_continuation` 解析；`ContinuationFormatError` 以及构造期的 `TypeError`、`ValueError` 都转成不带原值的 `SessionFormatError`。

**`continuation_contracts.py`**：只给 `_freeze_sequence` 补返回类型 `tuple[Any, ...]`，或与现有风格一致的等价注解。

## 实现要求

- 按 `docs/code_spec.md` §1.3 核对：版本常量的引用方（`jsonl_store.py`、`session_service.py`）都是通过常量取版本，不需要改代码；如果发现必须改禁止范围内的文件，停下来在汇报中说明，不要越界。
- 旧版本的读取分支只扩充，不放宽：v1～v5 的字段集合和校验规则保持原样。
- 测试中更新版本断言时，只把「当前版本」的期望值从 5 改为 6；断言读取旧版本时保留原版本号（例如 v4 样本读入后仍是 4）的断言不改。
- 不新增依赖。
- 契约里调用清洗判定只是兜底：Engine 交给轮次的消息已经清洗过，所以在这里无法发现原始工具参数里的凭据。按原始消息做判定，由第 3 步在 Engine 中负责；本卡不处理，只需在 docstring 里写明这个分工。

## 完成标准

- `CURRENT_SESSION_FORMAT_VERSION == 6`。新建的会话、v1～v5 升级后的会话，每行的 `format_version` 都是 6。
- v6 规范字节测试：一个带两步工具往返和最终回答的轮次，包含 Responses 续接（reasoning、text、tool_call 项）和一个 `null`，加上一个第一步带 Messages 续接的检查点。写出的字节与测试中的字面量完全一致，读回后对象与原对象相等。
- 新增 v5 固定样本：带 selection 的 v5 元数据、一条带工具的 v5 轮次、一条 v5 检查点。读取后文件字节不变，续接全部为 `None`。第一次业务写入后整文件升到 v6，selection、轮次和检查点内容与读取时相等。替换失败时原字节不变，之后重试成功。
- 以下每种情况都有测试，读取时得到 `SessionFormatError`，构造时得到 `ValueError` 或 `TypeError`，且异常文本不包含续接里的思考文本、签名或密文：
  - v6 `turn` 缺少 `continuations`；
  - `continuations` 长度与 assistant 消息条数不符；
  - 续接违反契约（例如未知项类型）；
  - 工具调用引用顺序与消息不符；
  - 单轮合计超过 1 MiB；
  - v5 `turn` 带 `continuations`；
  - v5 检查点的 progress 带 `continuation`；
  - v6 检查点的 progress 缺少 `continuation`。
- 构造时续接里的思考文本含本地绝对路径，保存下来的记录为不可回放。
- `TurnEntry`、`RunCheckpointProgress`、`RunCheckpoint` 的 `repr()` 不包含续接内容。
- 验证：
  - `uv run pytest -q -W error`（格式变更，跑全量；`test_distribution.py` 中依赖平台权限的既有跳过项如实列出）
  - `uv run ruff check src/mica_agent tests`
