## 目标

`error: storage: session persistence failed` 的真实来源，明确它究竟是 App 完成快照不满足提交不变量、
`TurnEntry` 构造失败、SessionService/JSONL 写入异常，还是测试资源生命周期问题。只有证据证明根因位于
本测试模块的装配或资源所有权时，才在该文件内做最小修复；如果证据指向产品代码，停止修改并向 master
提交可复核诊断，不得在测试任务中掩盖产品缺陷。

任务完成后，CLI 交互测试必须保持原有 36 个收集项和产品断言，持久化目录由一个明确所有者管理，且已知
失败路径在有界稳定性验证和一次全量验证中不再出现。不得把定向复跑偶然通过当作根因结论。

## 诊断与实现约束

### 1. 区分同一安全消息背后的失败分支

- 使用仓库外探针或测试内临时观测，分别记录 App 收到 `RunCompleted` 时 completed messages、tool
  presentations 的数量与结构，以及 `SessionService.commit_turn()` 是否被调用、是否抛出异常。
- 若 commit 抛错，记录稳定异常类型、异常链、store 操作阶段和必要的相对文件状态；不得输出凭据、绝对
  用户路径或完整会话正文。若 commit 未抛错却仍返回失败，定位是哪个完成快照或 `TurnEntry` 不变量未满足。
- 临时观测不能留在最终测试中，除非它本身成为有稳定价值的行为断言。

### 2. 核对真实生命周期

- 画清临时目录、workspace、data root、SessionService、Provider、MicaApp 和异步生成器分别由谁创建、持有、
  使用和释放；确认 provider `aclose()` 相对第二轮 commit、CLI EOF 和事件循环关闭的实际顺序。
- 检查失败后目录是否仍存在、session JSONL 与 lock/tmp 文件的状态、是否有未关闭句柄、后台 task、线程或
  async generator。不能因为目录最终为空就直接断定 Windows 文件系统竞态。

### 3. 有界复现与最小修复

- 先完成带诊断的单次目标场景，再根据已观察到的失败分支设计有上限的压力验证；每次运行都必须能输出
  成功/失败分支和资源状态，不进行无诊断的循环复跑。
- 如果根因是测试临时目录所有权或清理时机，使用职责最清晰的 pytest fixture 管理根目录，helper 只创建
  子路径，Provider 不再承担测试目录保活或清理。实现可以参考 T-007 的原则，但必须适配本文件自己的调用
  链并说明为何能消除已捕获的失败。
- 如果根因是产品完成快照、持久化或锁实现，停止在本任务中修改并给出最小复现、异常分支和建议写入范围，

## 候选经验

- 统一的安全错误文本只能证明 `_interact()` 消费到了对应 `RunFailed`，不能仅凭文本反推完成不变量、`TurnEntry` 或具体 store 操作。逐事件记录必须覆盖 App 终态事件、commit 返回值和 recorder 最终内容。
- `_run_selected_session()` 在 `_interact()` 返回后的 `finally` 中关闭 Provider；该 close 异常直接从 `run_interactive()` 传播，不会倒流为已经结束的 `MicaApp.run()` 的 storage `RunFailed`。资源清理 traceback 与 Run 内终态事件必须作为两条因果链分别验证。
- 测试 Provider 不应兼任测试临时目录所有者。当前 fixture 改动消除了已独立捕获的 WinError 145 cleanup failure，但任何绿色验证都不能替代对另一个历史失败的原始因果记录。
- 建议去向：作为测试资源生命周期与诊断证据规则留在任务记录；若 master 认为具有普适性，再由 master 评估是否提炼到长期规范。本 worker 不修改长期治理文档。
