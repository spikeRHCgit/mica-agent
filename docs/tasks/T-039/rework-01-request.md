## 1. 凭据提交与保护未确认的结果必须准确

- CredentialProtectionError 不等于“凭据已经提交”：它可能发生在目录/文件保护前检，也可能在替换后复核。create_connection/change_api_key 不能仅凭异常类型就把 credential 放进确定 completed。
- 不改底层异常类或配置格式，不依赖匹配异常文案猜测分支。无法可靠确认时使用 unconfirmed，明确待确认范围，不宣称已经完成或旧记录一定仍在。保留底层安全提示中“已替换但保护未确认”的真实含义；delete 中已确认的 models 提交仍须保留。
- 清楚约定 completed 是已确认完成的范围，remaining 在 unconfirmed 下是未完成/待确认范围，而不是“证明绝未写入”。不能用笼统提示掩盖自相矛盾的结构化字段。
- 补新增连接与改 Key 的写前保护失败回归，分别检查 auth 不存在/原字节未变以及结果字段；保留替换后保护未确认的真实字节、提示和结果保护。允许同步修正原先把未知提交写成确定 completed 的错误测试期望，但不得删除替换后保护回归。

## 2. 改 Key 后检查并报告可观测的 models 变化

- 保留写入前基线检查与 auth CAS；凭据正常提交后，再核对目标 models 基线。若已被并发改名/禁用/删除，不返回 complete 或旧 ConnectionSummary；明确 Key 已提交、连接状态已变化并要求刷新，状态可使用已有 partial/unconfirmed 等合适类别。
- 后验读取失败也必须保留“凭据保存已成功”的已确认事实，不伪装成整个操作未执行。不要因后验冲突回滚凭据，不重建被删 models，不重试覆盖并发编辑。
- 不要求消除所有跨文件窗口，不新增跨文件事务/锁或底层存储语义；后验快照形成后又发生的新变化仍按既有快照失效/for_run 规则处理。这里修的是“提交期间已发生且可检测的变化仍被报成完整成功”。
- 用权限/文件边界的确定性交错，在实际 auth 替换前执行另一窗口的真实 ConfigStore 禁用或删除；保持真实 CredentialStore 写入，检查磁盘和返回结果。不能把维护动作或 CAS fake 掉，也不靠 sleep 猜时序。

## 3. 隔离真正用于 CAS 的嵌套基线

- ConnectionEdit/CatalogDiscovery 持有的 models/auth 完整基线须免受消费者修改嵌套列表、字典和未知扩展的影响；顶层 MappingProxyType 不够。
- 可选内部深度不可变表示或防御性副本，保持短生命周期、隐藏 repr，无全局句柄表或凭据缓存。提供给既有存储的完整 JSON 记录仍须保持原有类型与值，不能因 tuple/list 差异让全部 CAS 失败。
- 补嵌套模型、列表和 auth 未知扩展的保护；可断言修改被拒绝，或修改返回副本后真正基线不变。随后用未被改写的原始基线做一次真实保存闭环，证明不是只“冻住数据”却破坏业务。不得泄露 Key、URL 或路径。
