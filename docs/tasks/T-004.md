# T-004 测试资产重编目与精简批次设计

状态：待开始 · 阶段：阶段间治理 · 负责：外部 worker · 分支：`task/T-004-test-audit` · 产品基线：`d3ed7ee`
依赖：T-001～T-003 已验收 · 提交授权：否，交付未提交改动

## 目标

对当前 `tests/` 做一次以稳定行为为中心的只读重编目，查明哪些测试是唯一保护、哪些重复证明同一事实、
哪些只依赖已经退役的实现或施工阶段命名，并形成可以直接派发的小批精简顺序。审计必须为每个合并、
改写、重命名或删除建议提供具体行为与替代证据，不以测试文件数量、代码行数、阶段编号或运行时间单独
决定删除。

本任务只产出事实清单和实施批次，不修改测试或产品代码；后续由 master 根据审计结果另开实现任务。

## 审计要求

1. **确认当前基线**：记录分支、HEAD、上游、工作区与 Python/pytest 环境；重新统计 Python 测试文件、
   pytest 收集项、各文件行数和收集项数。派工时的参考值是 57 个 Python 文件、1,778 个收集项，实际
   数字不同时以本任务 worktree 的可复核结果为准并说明差异。
2. **逐模块重编目**：覆盖全部 `tests/*.py` 与测试辅助模块。每个模块至少记录主要保护行为、所属层级
   （纯契约、组件行为、跨层生命周期、CLI/分发、平台/物理行为）、对应产品入口、独有高价值边界和
   初步处置（保留、合并、改写/重命名、候选删除或暂不判断）。不得只抽查大文件。
3. **建立必须保留清单**：明确标出兼容迁移、损坏数据、路径越界、凭据清洗、权限绕过、取消/资源
   清理、持久化原子性、安装分发和终端物理不变量等安全或兼容保护。文件名陈旧不影响其保留价值。
4. **证明重复或失效**：对每个候选合并/删除项，列出原测试文件与测试名、保护的输入/输出/失败模式、
   当前等价保护的文件与测试名，或对应产品行为已经退役的源码/Git 证据。无法完成一一映射的项目只能
   标为“待进一步调查”，不能进入删除批次。
5. **审查阶段号资产**：逐一检查所有 `test_p*_*.py`；判断它们应迁入哪个行为命名模块、是否与现有模块
   重复，以及哪些场景是仍需保留的跨层生命周期证据。阶段号本身不是删除依据。
6. **审查共享测试装配**：定位重复的 Provider、App、事件收集与终端 harness，比较其构造参数、状态和
   断言差异；只建议抽取真正稳定且窄小的公共协议，不设计隐藏大量默认行为的万能 `conftest.py`。
7. **审查等待与慢边界**：列出固定 `sleep`、真实墙钟等待、子进程、安装构建和平台相关测试，区分可由
   Event/队列/状态变化替换的猜测性等待，与确实验证时间或平台行为而必须保留的等待。
8. **形成实施批次**：按依赖关系拆成可独立验收的小批任务。每批必须写明目标、精确候选文件、保护的
   行为、拟采取的保留/迁移/合并/删除动作、所需验证和不能触碰的边界；优先处理证据最充分、范围最窄
   的重复资产，不在单批中混入产品重构。

## 验收

- 审计覆盖当前全部测试 Python 文件，没有只凭文件名或行数下结论。
- 每个候选删除或合并项都有“原保护行为 → 等价保留测试或行为已退役证据”的精确映射；安全与兼容
  负向测试没有在缺少等价保护时进入删除清单。
- 所有阶段号测试文件都有明确处置建议；所有重复 Provider/App/harness 候选都说明了实际差异，未
  提议万能 fixture。
- 固定等待、慢速边界和平台测试完成分类，模拟测试与真实环境证据保持区分。
- 产出按优先级和依赖排序的后续实施批次，首批足够小且可以直接据此编写下一张任务卡。
- 运行 `uv run pytest --collect-only -q -p no:cacheprovider` 并取得明确退出码；本任务不要求全量测试、
  Ruff、构建或真实终端验收，因为不修改产品或测试代码。
- `git diff --check` 与 `git diff --cached --check` 通过；实际 diff 只包含本任务卡授权追加区域，暂存区
  为空。
