**受限结论（仅限本次候选集运行）**

- 在**原始时间顺序**中，63 条成功 create 事件之后分别出现了与其 PID 对应的 close 事件（63 条 PID 非空的 close）。
- 两个被复用的 ID 在复用前，前一对象都已出现处于关闭状态的 `__del__`（`is_closing=true`）；复用后的第二个对象
  同样完成 create → close → 关闭状态 `__del__`。
- 两个启动失败对象也分别出现 close（PID 为空）与关闭状态 `__del__`。
- 本次候选运行**未观察到任何 `is_closing=false` 的 `__del__`**（0 条），`-W error` 下无任何 warning。
- 上述结论依赖**原始事件顺序**，而不是聚合账本；插件按裸 `id(transport)` 聚合，ID 复用会把两个对象的事件并入同一
  条目，因此聚合账本的 `tracked` / `closed` 只能读作“唯一 ID 数”，**不能**作为无歧义统计独立 transport 对象、
  也不能作为闭合的充分证明。

  GC 时机和会话上下文不同；原 warning 的真实创建者仍然**未确认**。

- **现象**：`id(object)` 只在对象存活期间唯一，对象销毁后可能被复用。本次候选组 63 条成功 create 事件只对应
  **61 个唯一 `transport_id`**，其中 2 个 ID 在“前一对象 create → close → `__del__`”完成后被新对象复用；
  因此按裸 `id()` 聚合的账本会把两个对象合并为一条，`tracked=63` 是“唯一 ID 数”，不是稳定对象身份，
  也不构成无歧义的闭合证明。
  **建议**：生命周期追踪若跨越对象销毁，必须使用“ID + 创建序号/代次（generation）”等稳定事件身份作为主键，
  不能把裸 `id()` 当永久主键。
  **证据位置**：`%TEMP%\t012_candidates.jsonl`（复用时间线见本卡表格）与只读复核脚本
  `%TEMP%\t012_identity_audit.py`。
  **建议去向**：暂留本任务卡候选经验，不直接修改长期规范。
- **现象**：`asyncio.create_subprocess_exec` 失败时（`Popen` 抛错），`BaseSubprocessTransport.__init__` 会先在
  异常分支 `close()` 再抛出；以“create 成功返回后才记录”为口径的追踪插件会看到“有 close、无 create”的记录。
  **证据位置**：`%TEMP%\t012_candidates.jsonl` 的 2 条无 create 记录。
  **建议去向**：`docs/lessons/inbox.md`（追踪类任务应在账目中单列“启动失败但已收口”一类）。
- **现象**：把“只创建、未收口”作为首要判定指标比“是否出现 warning”更稳，因为 warning 取决于 GC 时机；
  逐对象的 create/close 账目可在没有 warning 时仍给出确定结论。
  **证据位置**：本次候选组 `is_closing=false` 的 `__del__` 为 0。
  **建议去向**：`docs/lessons/inbox.md`。
- **现象**：`BaseSubprocessTransport.__del__` 触发时 `_proc` 可能已为 `None`，PID 需从 `create` / `close` 事件关联，
  `__del__` 只能用 `created_node` + 事件序号定位。
  **证据位置**：`%TEMP%\t012_smoke.jsonl` 与候选组日志中的 `del` 事件（`pid` 为 `null`）。
  **建议去向**：`docs/lessons/inbox.md`（与 T-011 已记录的同现象合并）。
