# Mica 代码审查、规范与优化实施计划

> 状态：进行中（当前步骤见 `docs/STATUS.md`）
>
> 生命周期：阶段间治理期的临时计划；治理收口后与 `docs/code_review_report.md` 一起删除（原文从
> Git 历史查看），仍然有效的规则和事实此前应已迁入 code spec、源码地图等长期文档。
>
> 本文规定阶段间代码治理工作的目标、执行顺序和验收边界。项目方向与架构上位约束见
> `docs/PROJECT_PLAN.md`，当前文件职责见 `docs/module_map.md`；本轮只读审查结论单独写入
> `docs/code_review_report.md`。

## 1. 工作目标

在不改变已验收产品行为的前提下，系统审查 Mica 当前架构、代码风格、注释和测试资产，建立一套
基于现有代码事实、能够约束后续 agent 开发的 code spec，并按依赖顺序清理历史包袱、修正结构性
问题和收敛测试体系。

本次工作的重点不是统一表面格式，而是解决以下问题：

- worker 围绕局部任务形成局部最优实现，缺少对系统链路、状态所有权和依赖方向的整体判断；
- 历史迭代留下并行路径、重复抽象、职责交叉或过度兼容时，缺少统一的识别和删除标准；
- 注释语言、位置和内容没有稳定规范，非显然决策与普通代码说明混杂；
- 测试围绕私有实现和单次返工持续增长，重复资产没有随功能替换及时合并或清理；
- 代码审查、实现、验证与文档同步没有共同遵守的项目级标准。

## 2. 执行原则

- **全局认识优先**：先还原关键运行链路、模块职责和状态所有权，再评价局部实现或安排重构。
- **证据支持结论**：问题必须指向实际代码、依赖、测试或可观察行为；文件长度、测试数量和个人偏好只能作为检查信号。
- **现状与目标分离**：审查报告描述当前事实和问题，code spec 定义以后应遵守的规则，整改任务负责把两者之间的差距逐步消除。
- **行为保持优先**：结构和风格优化默认保持已经验收的公共行为、持久化数据和终端交互；确需改变产品行为时另行讨论并明确验收。
- **删除需要证明**：删除代码或测试前确认其公共行为、安全边界和兼容价值已迁移、被替代或不再适用。
- **小批完整整改**：每个整改任务围绕一个可独立验收的架构边界，包含必要的代码、测试和文档同步，不进行跨系统的大爆炸式重写。

## 3. 审查范围

### 3.1 架构与关键链路

还原并审查以下链路：

1. CLI 启动、配置输入、工作区与会话选择、依赖装配和资源关闭；
2. 用户输入、MicaApp、AgentEngine、Provider、工具循环和唯一终态；
3. Tool Registry、Schema、Policy、Permission/Ask、handler 与结果回传；
4. 成功轮次、中断检查点、JSONL、恢复上下文和历史投影；
5. 终端输入、composer/interaction、语义块、差分渲染和物理输出；
6. Esc/Ctrl+C、取消令牌、异步任务、子进程、Provider 与前端关闭。

重点识别状态的唯一拥有者、依赖方向、跨层访问、并行实现、重复转换、生命周期分叉和扩展点是否
真正独立于核心循环。

### 3.2 代码结构与风格

审查模块、类和函数的职责与变化原因；命名、类型、可变状态、异常、异步代码和资源管理的一致性；
重复抽象、过度拆分、过度集中和只为历史实现存在的代码。文件行数和复杂度只用于定位候选热点，
不作为自动拆分标准。

### 3.3 注释与 docstring

区分解释设计原因、不变量、外部限制和兼容条件的有效注释，以及重复代码、记录施工过程、已经过时
或试图掩盖复杂实现的无效注释。审查语言混用、公共 API 文档缺失和注释与实现不一致的问题。

### 3.4 测试资产

把测试归类为公共契约、纯函数边界、模块集成、运行链路、CLI/分发、终端物理行为、历史兼容迁移
和安全负向测试，识别重复覆盖、私有实现耦合、历史资产、脆弱等待、过量 fixture 与缺少真实链路
证明的问题。测试代码量和测试数量不作为独立清理目标。

## 4. 实施阶段

### 4.1 全局只读审查

- 只读取和分析 `src/**`、`tests/**`、项目配置与现有事实文档；不修改产品代码和测试。
- 通过文件统计、依赖与导入关系、注释分布、测试收集信息和代表性链路追踪辅助判断。
- 对每项发现记录证据、影响、问题类别、置信度和建议优先级；没有证据的问题不写成确定结论。
- 产出 `docs/code_review_report.md`，同时列出尚需动态验证或用户决策的事项。

### 4.2 Code spec 讨论与定稿

- 结合审查结果和用户目标讨论架构、依赖、状态、错误、异步、注释、兼容与测试标准。
- 新建 `docs/code_spec.md`，用“简短总结：完整单条规则”的形式记录可执行规范。
- 项目 `AGENTS.md` 只保留 code spec 的启动路由和少量最高优先级原则，不复制规范正文。
- 对无法通过代码、测试或 review 执行的空泛原则不予收录。

### 4.3 分批整改

按以下依赖顺序制定任务，不要求机械地每类各建一个任务：

1. 删除已确认无调用的旧实现、并行路径和无价值兼容层；
2. 修正状态所有权、模块职责和依赖方向；
3. 合并重复模型与转换，收敛公共契约和生命周期；
4. 合并、改写或删除重复、过时和私有实现耦合的测试；
5. 在结构稳定后统一命名、注释、docstring 和局部实现风格。

每项整改任务以任务卡派发（`docs/tasks/README.md`），并必须说明所处系统链路、目标状态所有者、
允许改变的内部结构、必须保持的公共行为、测试资产处理方式和必要验证。不得用新的 adapter、兼容
分支或平行状态掩盖未解决的边界问题。

整改期间 `docs/module_map.md` 冻结（`docs/decisions.md` D-010）：整改任务不更新它，以
`docs/code_review_report.md` §4、任务卡「必读」和源码本身定位；4.4 收口时按 code spec 确定的
结构重写。

### 4.4 全局复验与收口

- 重新检查六条关键链路与模块依赖，确认没有产生第二套实现或新的反向依赖。
- 审计 tests 目录，确认留下的测试都能说明稳定行为或高价值边界。
- 按 code spec 确定的结构重写 `module_map.md`，并核对源码注释、code spec 和当前实现的一致性。
- 根据影响完成静态检查、聚焦测试、全量测试、离线构建和必要的真实 Windows Terminal 验收。
- 汇总仍被接受的复杂度与后续事项；完成用户审查后再做 Git 收口。

## 5. 只读审查报告要求

`docs/code_review_report.md` 至少包含：

- 当前代码与测试规模的可复核基线；
- 六条关键运行链路及主要状态所有者；
- 架构、实现、注释和测试发现，附具体文件或符号证据；
- 每项发现的影响、优先级、置信度和建议方向；
- 不应被误判为缺陷的合理复杂度；
- 建议进入 code spec 的候选规则；
- 建议的整改顺序，以及需要用户共同决定的问题。

报告不直接修改代码，不以测试数量或行数设删除配额，不把历史设计选择自动描述成错误，也不把尚未
验证的推断包装为事实。

## 6. 完成标准

本次代码治理工作只有同时满足以下条件才完成：

- 全局审查覆盖核心业务、终端前端、持久化、工具、Provider 和 tests；
- code spec 经用户确认，能够直接指导后续 agent 实现和 code review；
- 已确认的高优先级结构问题完成整改，公共行为和数据兼容边界得到验证；
- 重复或过时测试完成合并清理，测试体系能够以更少的实现耦合保护稳定行为；
- 源码、注释、测试和事实文档之间不存在已知冲突；
- 自动化、构建和必要的真实环境验收通过，并由用户批准最终收口。
