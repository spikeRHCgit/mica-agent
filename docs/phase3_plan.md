# Mica 第三阶段：标准会话、JSONL 持久化与上下文管理

> 状态：已完成
> 上位约束：`docs/PROJECT_PLAN.md`
> 前置阶段：`docs/phase2_plan.md`

## 1. 阶段目标

把基础对话从进程内消息历史扩展为按工作区隔离、退出后仍可恢复的标准会话。会话业务由 Session Service 拥有，文件可靠性由 JSONL Store 负责；应用只提交完整成功轮次，Provider、Engine 和终端前端都不直接修改会话文件。

## 2. 已交付能力

- 识别当前 Git 仓库根目录或非 Git 启动目录，建立稳定的工作区身份和独立会话目录。
- 为会话元数据与成功轮次建立供应商无关的数据契约；一个会话对应一个带显式版本及记录类型的 JSONL 文件。
- 支持会话创建、加载、列表、最后活跃选择、重命名、分支、回退、清空和过期清理，并从记录重建模型可用的消息上下文。
- 启动或恢复时加载全局和工作区 `AGENTS.md`，对不可读、超限或非法编码给出安全诊断，不修改已保存的对话。
- 基础 CLI 支持新建会话、`--continue` 和 `--resume`；成功对话写入后，退出并重新启动仍能携带先前上下文继续请求模型。
- 覆盖损坏文件、并发写入、原子替换失败、Windows 路径和仓库外安装态恢复等可靠性边界。

## 3. 具体实现

### 3.1 工作区与会话数据

`workspace.resolve_workspace()` 向上查找最近的 Git 根目录；找不到时使用启动目录。规范化绝对路径经 SHA-256 生成工作区 ID，再与安全 slug 组合为会话目录名。`session_contracts.py` 定义不可变的 `SessionMeta`、`TurnEntry`、显式记录类型和严格序列化/解析；成功轮次以用户消息、助手消息及其顺序为业务单位，不以原始 Provider 响应作为存储格式。

第三阶段首先交付成功轮次的会话格式。当前代码已由后续阶段升级至 v4，并兼容读取旧版本；中断检查点是第五阶段增加的能力，不回填为第三阶段的交付。

### 3.2 文件可靠性与会话业务

`JsonlSessionStore` 在单会话锁内读写 JSONL，逐条校验 UTF-8、JSON、版本、记录类型和记录顺序；追加成功轮次前检查已有内容。重命名、分支、回退及清空等整体变更通过同目录临时文件、`flush`/`fsync` 和 `os.replace` 完成，失败时保留旧文件；扫描会话目录时把损坏文件作为问题报告，不伪装成空会话。数据根目录可注入，测试不依赖真实 `~/.mica`。

`SessionService` 在 Store 之上实现会话选择、确定性列表排序、业务修改、上下文投影和 30 天未活动清理；当前使用或被保护、被锁定的会话不被清理。调用方得到不可变快照，CLI 和 App 不需要自行维护第二份可写历史。

### 3.3 上下文与运行提交

`ContextBuilder.build()` 依次读取全局、工作区 `AGENTS.md`，按字节上限与严格 UTF-8 校验后转换为带来源的系统消息，并分别返回安全诊断和成功加载来源；这些文件不复制进旧 `TurnEntry`。`MicaApp.run()` 将启动头部、`SessionService.context_snapshot()` 和本轮用户消息组成 `ProviderRequest`，由 Engine 推进；完整成功后通过 Service 提交 `TurnEntry`，存储失败转为明确的应用失败，而不是向前端报告成功。

`cli.py` 在装配单个会话 App 前解析新建、`--continue`、`--resume`，显式恢复无健康会话时返回诊断，不静默新建。历史上本阶段对失败、取消和提前关闭不写半轮成功记录；现行应用额外保存中断检查点，属于第五阶段的恢复扩展。

## 4. 验收结论

第三阶段已通过契约与损坏输入、并发和原子失败、工作区隔离、AGENTS 加载、成功轮提交边界、CLI 恢复及仓库外 wheel 继续对话的验证；静态检查、格式检查与离线构建通过。详细施工证据保留在 `docs/log/phase3_build_log.md`，当前用法和代码位置分别以 `README.md`、`docs/module_map.md` 为准。
