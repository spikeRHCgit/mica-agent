# Mica 第三阶段：标准会话、JSONL 持久化与上下文管理

> 状态：进行中
> 上位约束：`PROJECT_PLAN.md`
> 前置阶段：`docs/phase2_plan.md`

## 1. 阶段目标

第三阶段把第二阶段仅存在于 `MicaApp` 进程内存中的消息历史，升级为按工作区隔离、
可以可靠保存和恢复的标准会话。用户完成一次成功对话后退出 Mica，再次启动时可以
恢复同一会话并继续使用此前上下文。

本阶段建立三个长期边界：

1. Session Service 是会话元数据、轮次记录和上下文重建的唯一拥有者。
2. 一个会话对应一个带版本号的 JSONL 文件，Provider、Engine、CLI 和调试日志都不
   能成为会话真相源。
3. `MicaApp` 只在 `RunCompleted` 后提交完整用户消息和助手回复；失败、取消或消费者
   提前停止时不得留下半轮记录。

## 2. 用户可见结果

本阶段完成后提供以下基础入口：

```text
mica cli             # 在当前工作区创建新会话
mica cli --continue  # 恢复当前工作区最后活跃的会话
mica cli --resume    # 从当前工作区已有会话中选择一个
```

用户可以完成以下闭环：

```text
启动 Mica
  -> 创建或恢复当前工作区的会话
  -> 完成一轮或多轮对话
  -> 成功轮写入 JSONL
  -> 退出程序
  -> 再次恢复该会话
  -> 后续请求继续携带此前上下文
```

`--continue` 与 `--resume` 互斥。显式请求恢复但当前工作区没有可用会话时，CLI 必须
输出可操作诊断并以非零状态结束，不能静默创建新会话。`--resume` 本阶段只需要清晰、
可测试的基础编号选择，不提前实现最终 TUI 选择界面。

## 3. 构建范围

### 3.1 必须交付

- `SessionMeta`、`TurnEntry`、持久化记录类型、格式版本和会话错误契约。
- 一个会话一个 JSONL 文件，以及稳定的序列化、反序列化和完整校验。
- 会话按当前工作区隔离到：

  ```text
  ~/.mica/sessions/<workspace-slug>-<path-hash>/
  ```

- 工作区根目录、规范化路径、工作区 ID 和可读目录名的稳定生成。
- 可注入的 Mica 数据根目录；自动化测试不得读取或污染用户真实 `~/.mica`。
- 新建、加载、列出、选择最后活跃会话、重命名、复制、回退、清空和过期清理。
- JSONL 可靠追加、原子重写、会话级并发保护和损坏检测。
- 未知格式版本、未知记录类型、非法字段、截断行和无效编码的明确错误。
- 从会话记录重建供应商无关的标准 `Message` 上下文。
- 启动或恢复时加载全局与当前工作区 `AGENTS.md`，并返回可展示诊断。
- `MicaApp` 使用 Session Service，而不是自行拥有 `_history` 作为会话真相。
- 只有正常完成的 Run 提交 `TurnEntry`；失败、取消和提前停止不提交。
- `mica cli` 的新建、`--continue` 和 `--resume` 最小持久化闭环。
- 默认 30 天未活动会话清理，并保护当前使用或已锁定的会话。
- 单元测试、跨模块集成测试、Windows 路径测试和仓库外 wheel 恢复验证。
- README、阶段计划状态和阶段构建日志的 worker 侧收口。

### 3.2 明确不包含

- Tool Calling、工具消息、工具注册、权限判定和统一工具取消。
- Textual TUI、状态栏、弹窗、快捷键和最终会话选择界面。
- `/new`、`/rename`、`/branch`、`/rewind`、`/clear` 等最终斜杠命令；本阶段只完成
  它们依赖的 Session Service 能力和自动化测试。
- `/compact` 的摘要生成、token 阈值和压缩记录落盘。
- `/btw` 命令和旁路模型请求；本阶段只允许提供只读上下文快照能力。
- 最终配置系统、首次配置向导、模型发现与模型切换。
- ExtensionAPI、MCP、Skill 加载、npm 启动器和最终分发链路。
- GenericAgent 旧会话迁移、云同步、跨设备同步和工作区移动后的自动寻回。
- 把调试日志、Provider 私有对象或 UI 状态写入会话文件。

## 4. 阶段数据流与职责

```text
CLI 启动参数 + 当前工作区
  -> Workspace Resolver
  -> Session Service 创建或恢复会话
  -> Context Builder 加载 AGENTS 并重建 Message 上下文
  -> MicaApp 组装本轮用户消息
  -> AgentEngine / Provider 产生 EngineEvent
  -> 仅 RunCompleted 后生成完整 TurnEntry
  -> Session Service 提交
  -> JSONL Store 可靠写入
```

职责边界：

- Workspace Resolver 只确定工作区身份和数据目录，不读写会话业务记录。
- JSONL Store 只负责格式、校验、并发和可靠文件操作，不决定回退或清空语义。
- Session Service 负责会话业务操作和标准上下文，不调用模型、不渲染终端。
- Context Builder 组合 AGENTS 与会话消息，不改写历史，不改变权限。
- `MicaApp` 负责 Run 与提交边界，不直接打开、追加或重写 JSONL 文件。
- Engine 与 Provider 不持有会话，不读取 `~/.mica`，也不感知 `--continue`。
- CLI 负责解析用户选择和展示诊断，不自行修改会话文件。

## 5. 阶段契约

### 5.1 工作区身份

- 启动目录位于 Git 仓库内时，工作区根目录使用该仓库根目录；否则使用启动目录。
- 保存到元数据的工作区路径必须是规范化绝对路径；同一逻辑路径在当前平台上生成稳定
  的工作区 ID。
- 会话目录名由可读且经过安全处理的目录名 slug 与路径哈希组成。哈希必须足以避免
  常见同名目录冲突，具体长度由 P3-02 固定并测试。
- 工作区移动到新路径后视为新工作区，不自动猜测、合并或迁移旧会话。
- 文件系统和用户数据根目录必须由边界对象或构造参数注入，禁止测试修改真实 HOME。

### 5.2 `SessionMeta` 与 `TurnEntry`

公共数据对象必须供应商无关、可验证，并且不保存运行时私有对象。

`SessionMeta` 至少表达：

- 会话 ID、格式版本、标题；
- 工作区 ID 与规范化工作区路径；
- 创建时间与最后更新时间；
- 后续会话级配置可向后兼容扩展的明确边界。

`TurnEntry` 以一次成功的用户指令为最小业务单位，至少表达：

- 稳定的轮次 ID 和关联的 Run ID；
- 完整用户消息和完整助手消息；
- 创建或完成时间；
- 能够按持久化顺序无歧义重建标准 `Message` 的信息。

时间统一使用带时区的 UTC 表示；ID 是不依赖文件名含义的不可变唯一标识。当前阶段
只保存成功轮，不为失败或取消写入伪 `TurnEntry`。失败诊断仍属于 Engine 事件和界面，
不成为模型恢复上下文。

### 5.3 JSONL 格式与可靠性

- 文件第一条记录必须能够确定格式版本和完整 `SessionMeta`；后续记录表示会话内容。
- 记录必须有显式类型，读取器不得按字段形状猜测记录含义。
- 当前 writer 只写当前版本；reader 遇到未知版本或未知记录类型时明确失败，不能忽略。
- 读取时校验整份文件。空文件、缺少元数据、重复元数据、非法字段、坏行和截断尾行都
  视为损坏，返回不会泄露敏感内容的结构化错误。
- 成功轮使用会话级互斥保护后追加；重命名、复制、回退和清空等整体变更使用同目录
  临时文件、flush/关闭和原子替换，失败时保留原文件。
- 并发策略至少阻止两个进程同时写坏同一会话。若引入新依赖，worker 必须说明它实际
  消除的跨平台复杂度；不得仅为便利增加大型框架。
- 会话列表不得因为一个损坏文件而伪装成“没有会话”；应保留可定位诊断，同时允许
  调用方识别其他健康会话。

### 5.4 Session Service 行为

Session Service 对外提供业务意义明确的操作：

- 创建空会话并持久化元数据；
- 按 ID 加载，按最后更新时间倒序列出当前工作区会话；
- 选择当前工作区最后活跃的健康会话；
- 原子提交一个完整 `TurnEntry`；
- 重命名会话；
- 复制当前完整会话并生成新的会话 ID 和时间信息；
- 从指定 `TurnEntry` 开始删除该轮及其后续内容；
- 保留会话身份和标题、清空全部内容；
- 返回模型使用的不可变消息快照；
- 清理超过 30 天未活动且不是当前会话、也未被锁定的会话。

列表排序必须确定性；同一更新时间下使用稳定次级键。服务方法不得返回可被调用方
原地修改的内部集合。重命名、复制、回退和清空本阶段主要通过服务测试验收，CLI
无需提前暴露最终命令。

### 5.5 上下文与 `AGENTS.md`

AGENTS 只从两个稳定位置加载：

1. 全局 Mica 数据目录中的 `AGENTS.md`；
2. 当前工作区根目录中的 `AGENTS.md`。

全局内容先加入上下文，工作区内容后加入；用户当前明确指令的优先级仍高于普通
AGENTS 规则，内置安全边界始终不可覆盖。每次新启动或恢复都重新读取当前文件，
AGENTS 内容不复制进旧 `TurnEntry`，也不改写会话历史。

文件缺失时正常跳过；无法读取、无效 UTF-8 或超过限制时返回明确诊断，不静默忽略、
截断或把错误内容写入模型上下文。P3-04 必须用一个集中常量固定并测试每个文件的
大小上限，避免不同入口产生不同限制。

Context Builder 输出新的不可变标准消息序列。它可以在会话消息之前加入系统上下文，
但不能把 AGENTS 伪装成用户历史，也不能依赖 Provider 私有消息格式。当前阶段保留
未来增加非破坏性压缩记录的入口，但不得提前实现摘要算法或自动压缩。

### 5.6 `MicaApp` 提交与 CLI 装配

- `MicaApp.run(prompt)` 启动前从 Session Service 获取当前只读上下文，再追加本轮用户
  消息构造 `ProviderRequest`。
- 收到文本增量时只在本轮缓冲助手内容；只有收到 `RunCompleted` 后才一次性提交完整
  `TurnEntry`。
- `RunFailed`、`RunCancelled`、`asyncio.CancelledError`、消费者提前关闭流或持久化提交
  失败时，不提交半轮历史。
- 会话写入失败不能伪装为成功。应用层必须将其转换为前端可区分、不会泄露路径或敏感
  内容的明确失败；具体公共错误形态由 P3-05 在不破坏已有 Engine 终态契约的前提下固定。
- 同一 App 的活动 Run 并发保护、Provider 关闭语义和现有公开事件顺序继续成立。
- CLI 在创建或选定会话后装配单一 `MicaApp`。Provider 连接参数仍沿用第二阶段临时环境
  变量，本阶段不顺手建设最终配置系统。

## 6. 任务拆分

状态：已完成。

以及序列化、反序列化和校验测试。不得实现真实文件写入、CLI 或 App 集成。

状态：已完成；依赖 P3-01。

## 7. 测试与验收安排

### 7.1 自动化测试

- 公共模型的类型、必填字段、时间、ID、版本和往返序列化。
- 未知版本、未知记录、空文件、坏 JSON、截断尾行、重复元数据和无效编码。
- 同名工作区隔离、路径规范化、Git 根目录识别和 Windows 大小写/分隔符行为。
- 追加与原子重写失败时原文件保持完整，并发写入不会交错破坏 JSONL。
- 创建、列表排序、继续、复制、重命名、回退、清空和 30 天清理语义。
- 当前或锁定会话不被清理，损坏会话产生诊断但不伪装为空列表。
- 全局/工作区 AGENTS 的加载顺序、缺失、不可读、超限和无效编码。
- `RunCompleted` 提交；失败、取消、提前停止和提交失败不产生半轮记录。
- 退出后重新装配 App，恢复记录并在下一次 Provider 请求中携带完整上下文。
- `mica cli --continue`、`--resume`、互斥参数、无会话诊断和两个公共入口一致性。
- 默认测试不访问真实网络、不需要真实 Key、不读取或写入真实 `~/.mica`。

### 7.2 分发与仓库外验收

使用临时 HOME/用户数据根目录安装本阶段 wheel，在仓库外执行：

1. 启动 `mica cli` 并完成成功轮；
2. 退出后确认会话 JSONL 位于临时 Mica 数据目录；
3. 用 `--continue` 重新启动并确认下一次请求携带前文；
4. 确认未导入 GenericAgent 旧模块，未读取仓库内测试资源；
5. 确认 Key、完整模型响应和用户隐私内容没有进入诊断或构建产物报告。

### 7.3 阶段达标标准

第三阶段只有同时满足以下条件才算完成：

- 新建、退出、恢复和继续对话形成真实持久化闭环。
- 会话真相只属于 Session Service，Engine、Provider 和 CLI 没有私自持有第二份历史。
- 成功、失败、取消、提前停止和写入失败的提交边界都有自动化证据。
- JSONL 损坏与并发写入不会静默丢失或破坏已有健康数据。
- Session Service 的复制、回退、清空和清理能力通过测试，但未提前暴露最终命令界面。
- AGENTS 加载位置、顺序、限制和诊断符合项目计划。
- `uv run pytest`、Ruff 检查、格式检查与 `uv build --offline` 全部通过。
- 仓库外 wheel 的保存与恢复验证通过，默认测试未污染真实用户目录。
- README、本阶段计划与实际能力一致，没有引入第四、第五阶段范围。

## 8. 阶段构建日志责任

每张 P3 任务单都必须要求该 worker 创建或更新 `docs/phase3_build_log.md` 中与任务编号
对应的一个章节。章节只记录任务目标、设计思路、实现结构、关键取舍、交付成果和未来
学习入口；禁止命令流水、完整测试输出、大段源码、凭据和真实响应。

首个 worker 负责创建文件与 P3-01 章节，后续 worker 只维护自己的任务章节；返工直接
修订原章节，不追加返工时间线。该日志由 worker 自行保证准确、精炼和可供未来教学恢复，
不属于 master 主动读取或验收的材料，除非用户以后明确改变这一规则。

## 9. 风险与注意事项

- Windows 文件替换、打开文件和跨进程锁语义与 Unix 不完全相同；可靠性结论必须有
  Windows 自动化或最小真实文件验证，不能只凭 API 名称推断。
- 直接把 `Message` 列表序列化会丢失轮次边界，不能满足回退、复制和未来压缩需求。
- 把失败或部分流式文本写入恢复上下文，会让下次模型看到用户未认可的半成品回复。
- AGENTS 属于启动上下文而非历史记录；复制进每个 Turn 会造成陈旧规则和文件膨胀。
- `--resume` 的最终交互属于第五阶段。本阶段只建立可测试入口，不为临时界面扩展框架。
- 真实 HOME、真实会话和真实 Key 不得参与默认测试；测试注入边界必须在 P3-02 前固定。
