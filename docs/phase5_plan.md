# Mica 第五阶段：工具执行、权限控制与统一取消

> 状态：已批准，P5-01～P5-08 已验收，第五阶段代码构建与独立文档审查已完成
> 上位约束：`PROJECT_PLAN.md`
> 前置阶段：`docs/phase4_plan.md`
> 实施规则：按第 7 节依赖顺序逐项实施；未经 master 验收，不提前进入后续任务。

## 1. 阶段目标

第五阶段把 Mica 从“能够持续对话”升级为“能够在明确权限下操作当前工作区”。模型可以
请求工具，Mica 负责校验参数、判断权限、执行工具、把结果返回模型，并持续运行到得到
最终回复、发生失败、被取消或达到安全限制。

本阶段建立四个长期边界：

1. `ToolSpec` 是工具名称、说明和参数格式的唯一来源，模型、校验器和执行器使用同一份定义。
2. `ToolExecutor` 是工具执行的唯一入口；模型、Provider、Engine、CLI 和扩展不能绕过它。
3. `PolicyEngine` 在执行前返回 `ALLOW`、`ASK` 或 `DENY`，硬性安全边界优先于模式和允许规则。
4. Provider 请求、工具等待、子进程和用户取消共享同一取消信号；取消后不得继续执行或提交会话。

## 2. 用户可见结果

本阶段完成后，用户可以在基础 `mica cli` 中完成以下闭环：

```text
输入任务
  -> 模型请求一个或多个工具
  -> Mica 显示工具名称和必要的安全说明
  -> 需要授权时询问用户
  -> 工具执行并返回结果
  -> 模型根据结果继续工作
  -> 输出最终回答
  -> 整个成功 Run 作为一个完整轮次保存
```

阶段结束时交付五个内置工具：

| 工具 | 用户得到的能力 |
|---|---|
| `read` | 读取工作区内受大小限制的 UTF-8 文本文件 |
| `write` | 创建或完整替换工作区内的文本文件 |
| `edit` | 通过明确、唯一的旧文本匹配完成局部替换 |
| `bash` | 在当前工作区运行受超时、输出限制和取消控制的 Bash 命令 |
| `ask` | 模型暂停当前 Run，向用户提出一个问题并取得回答 |

不提供独立 `ls`；目录查看通过 `bash` 完成，并继续遵守命令权限确认。

基础 CLI 只提供清晰的文字提示和确认输入；完整 TUI、历史回放、状态栏、弹窗和快捷键
仍属于下一阶段。

## 3. 阶段主链路

一次用户指令仍然对应一个 Run，但一个 Run 可以包含多次模型请求和多次工具执行：

```text
历史 + 当前用户消息 + ToolSpec
  -> Provider 流式返回文本或工具调用
  -> Engine 组装并校验 ToolRequest
  -> PolicyEngine 决定 ALLOW / ASK / DENY
  -> ToolExecutor 执行或返回拒绝结果
  -> 工具结果作为标准消息追加到本 Run 上下文
  -> Provider 继续生成
  -> 最终助手回复
  -> MicaApp 只在 RunCompleted 后提交完整 TurnEntry
```

模型请求工具不表示 Run 完成。参数错误、未知工具、权限拒绝和普通工具失败应作为结构化
结果返回模型，使模型有机会改正；只有无法继续、用户取消或达到限制时才产生 Run 终态。

## 4. 构建范围

### 4.1 必须交付

- 供应商无关、不可变的 `ToolSpec`、`ToolCall`、`ToolRequest`、`ToolResult` 公共数据契约。
- 工具注册、名称冲突检查、工具列表快照、参数校验和统一执行入口。
- `PolicyDecision`、三种权限模式、硬性拒绝规则和一次性用户授权。
- `CancellationToken` 及 Provider、Engine、工具、等待和子进程的一致取消行为。
- 工具开始、结束、权限询问、用户提问、限制失败等有序 Engine 事件。
- 五个内置工具，以及工作区路径、符号链接、文件大小、输出大小、超时和进程回收边界。
- OpenAI-compatible Chat Completions 工具声明、流式工具调用组装和工具结果消息转换。
- Engine 的多步模型—工具循环、确定性顺序和模型调用/工具调用上限。
- 同一模型响应包含多个工具调用时按返回顺序逐个校验、授权和执行；本阶段不并行执行。
- 基础 CLI 的工具状态展示、权限确认、`ask` 回答和 `--permission-mode` 选择。
- 带工具过程的完整会话保存与恢复，以及现有纯文本会话的兼容读取和安全升级。
- 默认自动化测试、真实文件/子进程测试、仓库外 wheel 验收和一次受控真实 Provider 冒烟测试。

### 4.2 明确不包含

- Textual TUI、历史消息回放、状态栏、弹窗、最终快捷键和会话选择界面。
- `/new`、`/rename`、`/branch`、`/rewind`、`/clear`、`/btw`、`/compact` 等斜杠命令。
- JSON 配置文件、首次配置向导、模型发现和模型切换。
- ExtensionAPI、第三方工具自动发现、MCP Client、Skill 加载和远程工具。
- npm 启动器、PyPI/npm 正式发布、自动升级和公开 `0.1.0`。
- 浏览器控制、计算机控制、Git 自动提交、云同步和工作区文件回滚。
- 并行工具执行、后台自治任务、定时任务和多 Agent 编排。
- 依靠提示词代替参数校验或权限判定。

## 5. 公共契约

### 5.1 标准消息与工具对象

- 现有纯文本 `Message(role, content)` 构造和相等性保持兼容。
- 标准消息增加表达“助手工具调用”和“工具结果”的能力，但不得保存 Provider 私有对象。
- 工具调用至少包含稳定调用 ID、工具名和完整参数；流式参数在 Provider 边界组装完成后再进入 Engine。
- 工具参数和结果只允许可验证的 JSON 兼容数据；公共快照不能被调用方原地修改。
- 不可变 JSON 快照转换回普通 JSON 值时必须使用一个集中、纯函数入口；Provider 与会话层
  不得各自实现不同的递归转换规则。该入口在第一个真实 JSON 消费方任务中补齐并复用。
- `ToolResult` 明确区分成功、参数错误、未知工具、权限拒绝、执行失败和取消。
- 面向用户的事件与错误不得回显原始异常、未清洗命令输出、密钥或敏感文件内容。

参数校验必须以 `ToolSpec` 的 JSON Schema 为依据。实现任务需先做小型依赖审计：优先采用
成熟、体积合理的标准校验库；如果不用依赖，只允许实现 P5 明确需要的 Schema 子集，不能
声称支持完整 JSON Schema。

### 5.2 ToolRegistry 与 ToolExecutor

- 注册表拒绝空白名、非法名和重复名，并返回确定性、不可变的工具快照。
- 执行顺序固定为：查找工具、校验参数、规范化安全输入、权限判定、执行、清洗结果。
- Provider 只接收公开 ToolSpec；不得获得执行函数、路径对象、权限对象或内部注册表。
- Engine 不按工具名称写 `if/elif` 分支；新增工具只通过注册发生。
- 工具实现不得直接修改会话、调用 Provider 或伪造 Engine 终态。

### 5.3 权限模式

权限判定顺序固定为：

```text
硬性拒绝 -> 当前 Run 的一次性授权 -> 允许规则 -> 当前权限模式
```

本阶段允许规则通过构造参数注入，不提前读取未来的 `config.json`。

| 操作 | `default` | `accept_edits` | `solo mode` |
|---|---|---|---|
| 普通 `read` | ALLOW | ALLOW | ALLOW |
| 工作区内 `write` / `edit` | ASK | ALLOW | ALLOW |
| 明确只读且在安全清单内的命令 | ASK | ASK | ALLOW |
| 其他命令 | ASK | ASK | ASK |
| 敏感路径、越界路径或硬性危险操作 | DENY | DENY | DENY |
| `ask` | ALLOW | ALLOW | ALLOW |

`solo mode` 不等于取消安全边界。没有操作系统级沙箱时，不得宣称任意命令可以被可靠静态
分析；不能证明安全的命令保持 `ASK`，而不是为了“自动化”直接放行。当前基础 CLI 不生成
`SAFE_READ_ONLY_COMMAND` 分类，而是把全部 `bash` 调用归为 `COMMAND`，因此三种模式下 Bash
均询问；该安全只读分类只是可注入的 Policy seam，当前尚未启用。

### 5.4 用户等待与取消

- Engine 通过结构化事件声明权限请求或 `ask` 请求，不直接读取 stdin，不依赖 CLI。
- CLI 收到事件后读取用户选择，再通过 MicaApp 的公开响应入口恢复同一个 Run。
- 等待用户输入期间 Run 仍然活动；不得产生伪完成事件或写入半轮会话。
- `Ctrl+C`、任务取消、EOF 或消费者提前关闭必须唤醒所有等待，关闭 Provider 流，并终止活动子进程。
- 每个 Run 仍然只有一个终态；终态后忽略迟到的工具、权限和输入响应。

### 5.5 Provider 与 Engine

- `ProviderRequest` 增加不可变 ToolSpec 快照；没有工具时必须保持现有纯文本载荷和行为。
- OpenAI-compatible Provider 负责把 ToolSpec 转为 `tools` 请求字段，并组装流式 `tool_calls`。
- 工具调用 ID、名称或参数缺失、冲突、重复结束或 JSON 不完整时返回安全的畸形响应错误。
- 同一流出现任何文本或工具调用增量后，传输失败不得重发请求，避免重复工具意图。
- Engine 为同一 Run 维护标准消息，不保存 Provider 私有 chunk；工具结果追加后发起下一次模型请求。
- 达到模型步数或工具调用数上限时产生明确的限制终态，不继续调用 Provider 或工具。
- 普通工具失败和权限拒绝返回模型；取消、内部不变量破坏或耗尽上限才结束 Run。

### 5.6 会话格式与提交边界

工具过程必须能够在退出后恢复，否则模型可能重复已经执行过的副作用。P5 将会话格式升级
为 v2，并遵守以下兼容规则：

- reader 同时读取现有 v1 纯文本会话和新的 v2 工具会话；writer 只写 v2。
- P5-07 完成前，v1 只允许保存现有纯文本轮次；任何中间任务不得把带工具字段的 Message
  交给 v1 serializer 后声称工具历史已经持久化。
- v1 会话保持可列出、加载、继续、复制、回退、清空和删除。
- 第一次修改 v1 会话时，在同一个会话锁内原子重写为 v2；失败时原始 v1 字节保持不变。
- 现有 `TurnEntry.user_message`、`assistant_message` 和纯文本上下文行为保持兼容。
- v2 在一个 TurnEntry 内保存用户消息、按顺序发生的助手工具调用、工具结果和最终助手消息。
- 只有整个 Run 正常完成才提交 TurnEntry；失败、取消、等待中断或消费者提前关闭不提交半轮。
- 工具已经产生的工作区副作用不承诺回滚；后续模型请求失败时必须明确提示用户检查工作区。
- 持久化前清洗工具参数和输出中的常见凭据；不得保存原始异常、Provider chunk 或 UI 状态。

## 6. 内置工具安全边界

- 所有路径先相对工作区解析、规范化并检查真实目标；绝对路径、`..`、符号链接和重解析点
  不得绕过工作区边界。
- 已知凭据文件和凭据存储默认硬性拒绝读取或写入；具体清单集中定义并测试，不散落在工具中。
- `read` 和命令输出使用集中大小上限；超限时明确截断标记或失败，不能无限进入模型上下文。
- `write` 与 `edit` 使用同目录临时文件、flush、fsync 和原子替换；失败时保留原文件。
- `edit` 默认要求旧文本只出现一次；零次或多次匹配都失败，不猜测修改位置。
- 命令使用明确选择的可执行文件和参数启动，不使用 Python 隐式 `shell=True`。
- 子进程具有工作区 cwd、环境变量副本、超时、输出限制和进程树回收；取消后不得遗留后台进程。
- 工具错误返回固定、安全、可操作的摘要，不把完整路径、环境变量或原始异常写入事件。

## 8. 测试与验收

默认测试不得访问真实网络、真实 HOME、真实 Key 或工作区外用户文件。至少覆盖：

- 公共对象不可变性、严格类型和旧纯文本构造兼容。
- Schema 缺失字段、额外字段、类型错误、未知工具和重复注册。
- 三种权限模式、硬性拒绝优先级、一次性授权和用户拒绝。
- 路径穿越、绝对路径、符号链接/重解析点、敏感路径和大小边界。
- 原子 write/edit 失败时原文件不变、临时文件清理并可恢复执行。
- 命令成功、非零退出、启动失败、超时、输出超限、取消和子进程树清理。
- 权限等待与 ask 等待期间取消、EOF、迟到响应和消费者提前关闭。
- SSE 工具参数分片、多工具调用、文本与工具混合、畸形 JSON 和中途断流。
- Engine 多次 Provider 请求、顺序工具结果、失败恢复、调用上限和唯一终态。
- v1 会话读取、首次写入原子升级、v2 往返、损坏扫描和并发写入回归。
- 工具 Run 成功后恢复完整上下文；失败、取消或存储失败不产生半轮。
- `mica cli` 三种权限模式、确认/拒绝/ask、无配置安全失败和 Provider 关闭一次。

阶段达标还必须通过：

```text
uv run pytest
uv run ruff check src/mica_agent tests
uv run ruff format --check src/mica_agent tests
uv build --offline
git diff --check
```

安装态验收使用临时 HOME 和仓库外工作区，完成一次真实的“模型请求工具 -> 用户授权 ->
工具执行 -> 模型最终回答 -> 退出 -> --continue 恢复”闭环。真实 Key 只来自本机环境变量，
不进入测试输出、文档、日志、会话或提交。

## 9. 文档与 Git 责任

- 每个 worker 只维护自己的 P5 任务范围、测试和 `docs/phase5_build_log.md` 对应章节。
- 构建日志只记录目标、设计、关键取舍、成果、风险和学习入口，不记录命令流水或敏感内容。
- README 只在能力真实可用后更新，不能把计划中的工具写成已经实现。
- master 在每张任务验收后更新本计划状态，并负责阶段结束时的 Git 收口。
- 不执行未经用户授权的 reset、clean、历史重写、发布或远程推送。

## 10. 已确认的阶段决定

### 10.1 命令工具名称

公开工具名固定为 `bash`，与 `PROJECT_PLAN.md` 保持一致。Windows 端必须显式发现并启动
受支持的 Bash 环境；缺少可用 Bash 时返回安全、可操作的错误，不以 PowerShell 冒充
`bash`，也不使用 Python 隐式 `shell=True`。具体发现顺序和可注入测试边界由 P5-04 确定。

### 10.2 阶段编号与 UI 边界

本计划把工具与权限确定为 P5，把最终 TUI 保留给后续独立阶段。P5 的 CLI 只提供测试真实
工具闭环所需的文字提示，不借机建设半套 TUI。本边界已由用户批准，属于正式阶段约束。

## 11. 主要风险

- Windows 是本阶段命令工具的首要实现和真实验收平台。POSIX 适配应保留清晰边界和自动化
  测试，但未在 POSIX 环境实测前必须明确记录为剩余风险，不能宣称已经完成跨平台验收。
- 任意 shell 命令无法仅靠字符串分析获得真正沙箱保证；权限询问、工作区 cwd 和硬性拒绝
  是边界，不应被描述为操作系统隔离。
- Provider 可能以不同碎片顺序返回工具调用；组装错误会执行错误参数，必须先完整验证再执行。
- 工具产生副作用后模型仍可能失败；会话不写半轮并不等于工作区能够自动回滚。
- v1 到 v2 的升级涉及用户已有会话，任何失败注入都必须证明原字节可恢复。
- 工具输出和参数会进入模型上下文与成功会话，必须在进入两者之前应用统一的大小限制和凭据保护。
