> 阶段交付见 `docs/phase3_plan.md`；当前代码位置见 `docs/module_map.md`。除 P3-01 外，现存任务记录未保存可核实的 worker 返工过程；设计时规避的风险会明确标出，不写成已发生的失误。

## P3-01：会话公共数据契约

- 初始目标：先为后续 Store、Service 和上下文重建固定成功轮次的纯数据含义与单条记录转换边界，不提前实现文件或运行时功能。
- 实施经过：
  1. 用公开行为测试固定构造、解析和导入边界；复用既有 `Message`/`MessageRole`，实现不可变 `SessionMeta`、`TurnEntry`。
  2. 加入显式 `session_meta`/`turn` 类型、v1 版本及纯序列化/反序列化；一次成功用户指令保留为一个 Turn，而非扁平消息列表。
  3. 补顶层导出、惰性导入和安全诊断测试，再做静态检查、全量测试与离线构建。
- 实际失误与修正：首轮 Ruff 检查发现导入顺序、时间写法和测试格式问题，限定在本任务文件内修正；早期构建日志路径被 `.gitignore` 的 `**log.*` 忽略，普通状态检查未显示该文件。worker 核对忽略规则后未擅自扩大修改范围，任务提交时才加入针对阶段日志的例外。测试先红灯属于预定的测试先行过程，不计为产品缺陷。
- 结果与验证：构造错误保留 `TypeError`/`ValueError`；不可信 wire 的字段、角色、版本和 UTC 时间错误统一转为不回显内容的 `SessionFormatError`。构造、往返、安全诊断及纯导入测试通过，当时的全量测试、Ruff 和离线构建通过。
- 后续变化：第四阶段扩展工具消息和展示快照，第五阶段增加中断检查点与 v4；这些不是 P3-01 当时交付的能力。

## P3-02：工作区识别与 JSONL Store

- 初始目标：在公共契约之下提供稳定工作区身份和可靠的单会话文件原语，把文件正确性与会话业务分开。
- 实施经过：
  1. 从启动目录定位最近的 Git 根或使用非 Git 启动目录，以规范路径 SHA-256 和安全 slug 区分同名工作区。
  2. 用完整 session ID 哈希生成文件与锁名，建立元数据首行、成功轮次后续行的严格 JSONL 读写。
  3. 加入单会话锁、同目录临时文件与扫描诊断，再覆盖并发及失败恢复。
- 问题处理：留存记录没有可核实的施工返工。设计时针对两类风险作了防护：Unicode casefold 后再次过滤 slug，避免生成不安全字符；逻辑追加也采用 `flush`/`fsync` 后原子替换，而非裸追加，避免中断留下半份会话。Windows/POSIX 文件锁配合进程内线程锁，锁文件释放后保留以避免 inode 竞态。
- 结果与验证：Store 严格检查 UTF-8、重复 JSON key、记录顺序、跨记录唯一性和时间顺序；单个损坏文件不会让健康会话从扫描结果消失。工作区隔离、确定性序列化、原子替换失败后原字节保持与重试、跨线程/进程并发均有测试。

## P3-03：Session Service 会话操作

- 初始目标：让 Service 成为唯一会话业务拥有者，集中处理创建、选择、提交、历史变更、上下文投影和 30 天过期清理，不把业务策略放进 Store 或 App。
- 实施经过：
  1. 在 Store 原语上实现注入时钟和 ID 的创建、列表、提交、重命名、分支、回退、清空与只读上下文。
  2. 为清理增加窄的 `try_delete()`，由 Store 非阻塞取得单会话锁并在锁内重载、比对预期快照。
  3. 由 Service 判断期限与当前会话保护，区分已删、锁定、变化和损坏等结果，并补相应测试。
- 问题处理：留存记录没有可核实的施工返工。设计时识别了“锁外扫描后直接删除”会误删已变化会话的竞态，因此把最终快照复核移进锁内；分支、回退和清空统一采用不回拨的活动时间，避免历史修改让会话排序倒退。
- 结果与验证：健康列表按 `updated_at` 降序、session ID 升序排列；上下文只从已保存的完整轮次按顺序投影。时间与 ID 注入、排序、历史变更、受保护或锁定会话、锁内变化、删除前损坏和上下文不可变性均有回归测试。

## P3-04：上下文重建与 AGENTS.md 加载

- 初始目标：独立构建供应商无关的上下文，按固定来源顺序读取全局和工作区 `AGENTS.md`，与会话历史组合，但不写回会话文件。
- 实施经过：
  1. 定义不可变的结果、来源和诊断对象，固定全局与工作区文件的位置和顺序。
  2. 每次 `build()` 校验输入历史，再依次读取两个来源，把有效非空内容各作为一条系统消息放在历史之前。
  3. 加入单文件大小、编码与来源隔离测试，确认每轮重新读取而非缓存。
- 问题处理：留存记录没有可核实的施工返工。为避免截断指令被当成完整规则，读取量限制为 64 KiB 加一字节，超限整体跳过，合格后才严格 UTF-8 解码；缺失文件正常跳过，其他无效来源只给固定安全诊断，仍继续处理另一来源。
- 结果与验证：Builder 不创建目录、不写 Store/JSONL，诊断不包含路径、正文或原始异常。来源顺序、缺失与空文件、超限、非法编码、重新读取、输入不变性及无会话写入均有测试。

## P3-05：MicaApp 与基础 CLI 持久化闭环

- 初始目标：移除 App 的第二份可写历史，接通成功 Run 的持久化提交与新建、继续、编号恢复入口，使退出后的下一次进程能沿用会话。
- 实施经过：
  1. 让 App 每轮从 Service 快照与 Context Builder 组合请求，仅缓存本轮流式文本。
  2. 收到完整 `RunCompleted` 时构造并提交 `TurnEntry`，提交成功后才向前端转发终态；存储失败走应用失败路径。
  3. 让 CLI 在环境与工作区确定后选择或创建会话、预检上下文，最后才创建 Provider；再覆盖两轮恢复与异常路径。
- 问题处理：留存记录没有可核实的施工返工。设计时处理了两个容易导致假成功的边界：若先转发完成事件再落盘，存储失败会误报成功，因此改发 `RunFailed(STORAGE)`；若把 AGENTS 系统指令或未完成流写入 Turn，恢复历史会失真，因此只保存完整成功轮次的用户/助手内容。
- 结果与验证：CLI 支持默认新建、`--continue` 和健康会话的编号 `--resume`；默认新建立即持久化，即使随后空白输入或 EOF。App、Store 与 Builder 两轮恢复、失败/取消/提前关闭不写半个成功 Turn、写入失败时原 JSONL 字节不变，以及 CLI 非法选择均有回归测试。
- 后续变化：第五阶段另外增加中断检查点；本任务的“不写半轮”仅指不伪造完整成功的 `TurnEntry`。

## P3-06：集成验证、README 与阶段收口

- 初始目标：在仓库外安装态验证真实 CLI 的跨进程会话恢复，并让 README 与第三阶段已交付能力一致，不扩大产品功能。
- 实施经过：
  1. 用完整 wheel/venv fixture 和本机 loopback HTTP/SSE 服务提供确定的模型流。
  2. 在仓库外、含 Unicode 与空格的临时工作区运行已安装的 `mica`，隔离 HOME、USERPROFILE、数据根与 Python 导入环境。
  3. 分别执行首轮对话和新进程的 `--continue`，通过公开 Store/Service 接口检查文件及请求历史，再更新 README。
- 问题处理：留存记录没有可核实的施工返工。为防止源码导入或真实服务偶然成功掩盖安装问题，测试只经过安装入口与公开持久化结果，不使用真实 Provider 或凭据；异常写入可靠性继续由 Store 的故障注入测试覆盖。
- 结果与验证：第二次启动复用同一工作区会话，Provider 请求按顺序包含上一轮 user/assistant 与本轮 user，JSONL 留下两个完整轮次；会话文件只落在隔离数据根，没有 `AGENTS.md` 时也不凭空加入指令。
