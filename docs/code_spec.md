# Mica 代码规范

> **状态**：讨论稿，待用户确认后定稿。
>
> **文档职责**：本文规定 Mica 产品代码、测试代码和 code review 共同遵守的长期工程规则，用于
> 判断代码应该放在哪里、状态由谁拥有、模块如何协作、注释如何编写以及测试做到什么程度。
>
> **内容边界**：产品方向与长期架构见 `docs/PROJECT_PLAN.md`；当前文件位置见 `docs/module_map.md`；
> 阶段任务见 `docs/phaseN_plan.md`；决策理由见 `docs/decisions.md`；施工过程与
> 历史证据见对应构建日志。本文不记录任务进度、临时方案和针对单次缺陷的补丁要求。

## 1. 使用方式

- **规范先于模仿**：实现和审查代码时以本文为准，不因为现有代码采用了某种写法就默认该写法正确；现有代码与本文冲突时，将其视为待整改问题，不在新代码中继续复制。
- **规则结合事实**：规则用于指导判断，不能代替对实际调用链、状态、依赖和运行结果的检查；文件长度、函数数量和测试数量只能触发审查，不能单独证明设计有问题。
- **行为变更分开讨论**：代码整理和架构重构默认保持已验收的产品行为、公共契约、持久化数据和终端交互；需要改变产品行为时，必须另行说明目标与验收方式。
- **规范修改需要证据**：只有同类问题反复出现、现有规则持续导致错误判断，或项目方向发生稳定变化时，才修改本文；单次偶发问题不直接上升为长期规范。

## 2. 架构与职责

这一部分解决三个问题：一项逻辑应该放在哪个模块，哪个对象负责保存状态，以及模块之间允许怎样
调用。

- **完整链路优先**：开始实现前先确认需求经过的入口、核心流程、外部边界、持久化和前端投影，避免只在最先找到的局部文件中追加逻辑。
- **职责归属明确**：每项业务规则、状态转换或外部适配只能有一个主要负责模块；其他模块只能调用其公开能力，不得复制同一判断。
- **状态只有一个主人**：一项可变状态只能由一个对象创建、修改和结束；其他对象通过不可变值、事件或窄接口观察，不得共同维护多份需要相互同步的副本。
- **事实来源唯一**：同一业务事实只能有一个权威来源；缓存、展示模型和序列化数据必须能够追溯到该来源，不能反过来成为第二套业务状态。
- **数据单向流动**：核心链路中的数据应按明确方向从输入边界进入业务层，再以结果或事件返回；禁止依靠跨层回调、共享容器和隐藏副作用拼装完整结果。
- **依赖指向契约**：核心模块依赖稳定数据模型或协议，不得为了类型别名、工具函数或便利入口反向依赖具体 Provider、内置工具、前端或存储实现。
- **跨模块禁止私有导入**：以下划线命名的符号只供本模块使用；确需跨模块复用时，应先把它提升为职责明确的项目内部契约，而不是直接导入或复制实现。
- **公开层级清晰**：代码必须区分长期兼容的公共 API、项目内部跨模块契约和模块私有实现；只有经过明确决定的符号才能从顶层包导出。
- **扩展只走正式入口**：新增工具、Provider、命令或其他扩展能力必须通过对应注册和公共契约接入，不得要求修改 Agent Engine 的核心循环或绕过权限、校验与会话边界。
- **前端只负责交互投影**：CLI/TUI 可以管理输入、显示和前端局部状态，但不得重新定义业务终态、权限结果、工具结果或会话事实。
- **持久化保持供应商无关**：会话只保存经过清洗、可验证并足以恢复真实进度的标准数据，不持久化 Provider 私有对象、前端组件或调试状态。
- **复杂度按变化原因拆分**：模块同时承担多个能够独立变化的职责、出现反向依赖或拥有多个无关状态时才拆分；不得只为缩短文件或函数而制造大量薄包装。

## 3. 实现与数据边界

这一部分规定具体代码怎样保持清晰、可靠，并且在失败和取消时仍然能够解释。

- **最小完整实现**：实现只覆盖当前已经确认的需求，同时包含根因修复、必要契约、资源清理和验证；不得提前建设假设中的未来框架，也不得以缩小改动为由留下半条链路。
- **优先复用稳定语义**：已有模块确实拥有所需职责时复用其能力；只有新职责能够独立演进或现有抽象无法表达需求时才增加抽象，并说明不能复用的原因。
- **不保留无价值兼容层**：内部实现被替换后直接迁移调用方并删除旧路径；只有已确认的公共 API、持久化格式或外部协议需要兼容时，才保留有期限和测试证明的兼容逻辑。
- **边界完成校验**：CLI、Provider、JSONL、工具参数、文件路径和终端输入等外部数据必须在进入业务逻辑前完成类型、范围和安全校验；内部代码使用已经验证的强类型值。
- **转换集中完成**：同一种外部数据到内部模型的转换只能有一处正式实现；序列化、反序列化、清洗和展示转换不得在多个消费者中各写一套近似逻辑。
- **不可变值优先**：跨模块传递的消息、事件、配置快照和持久化记录优先使用不可变强类型对象；可变容器只留在明确的状态所有者内部。
- **函数只完成一个步骤**：函数应围绕一个可以清楚命名的动作组织；如果函数同时推进多个生命周期、维护多组无关状态或需要跨越很长距离才能理解，应按完整步骤提取，而不是机械切成碎片。
- **副作用必须可见**：文件、网络、进程、终端、环境变量和持久化写入只能发生在名称与职责能够体现这些副作用的边界中；纯转换和校验函数不得隐藏 IO。
- **资源由创建者收口**：创建异步任务、文件句柄、网络客户端、终端模式或子进程的对象负责正常完成、失败和取消路径上的释放；所有权转移必须通过明确接口表达。
- **取消属于正常路径**：异步代码必须显式传播并收敛取消，不得吞掉 `CancelledError`、把取消包装成未知失败，或在取消后留下任务、子进程和未完成持久化状态。
- **终态只能出现一次**：一次 Run、工具调用或交互必须只有一个可观察终态；完成、失败和取消不能通过多个分支重复提交或重复发送。
- **异常只在边界转换**：只在能够增加稳定语义、保护敏感信息、执行清理或转换为公共错误的边界捕获异常；宽泛捕获必须说明边界目的，不得静默吞错。
- **诊断不泄露敏感信息**：错误、日志、repr、会话和工具展示不得泄露凭据、本地绝对路径、未清洗参数或 Provider 原始响应；安全诊断应保留定位所需的稳定上下文。
- **持久化变更必须迁移**：修改会话或配置格式时必须定义版本、严格读取、原子写入、旧数据迁移和失败恢复；不得通过宽松解析把损坏数据当成有效数据。

## 4. 命名、注释与代码风格

这一部分不追求表面统一，而是让下一位维护者能够判断代码的真实意图。

- **标识符使用英文**：模块、类型、函数、变量、枚举、字段和稳定 wire value 使用含义明确的英文名称，避免缩写、音译和同一概念多种叫法。
- **注释范围保持明确**：本节所称注释包括 `#` 注释和 docstring；面向用户的界面文本、错误消息、日志、提示词、协议值和测试样本属于产品或测试数据，不得为了统一注释语言而机械翻译。
- **源码注释统一使用英文**：所有源码注释和 docstring 使用简洁、准确的英文；项目 Markdown 文档继续使用中文，代码标识符、协议名、命令和异常类型保持原始英文形式。
- **注释只解释非显然信息**：注释用于说明设计原因、不变量、状态所有权、外部限制、兼容条件、安全边界、取消与清理语义以及容易误改的风险；不得逐句复述代码，也不得用长注释掩盖职责混乱的实现。
- **施工历史不得进入源码**：阶段号、任务号、worker 名称、返工过程、临时结论和已经完成或尚未批准的未来计划写入对应任务或历史文档，不得留在源码注释和 docstring 中。
- **公共契约说明稳定边界**：公共类型、协议和入口的 docstring 应说明职责、输入输出、失败语义和关键限制；模块与类的 docstring 只概括角色和边界，简单私有函数只有在行为不显然时才需要 docstring。
- **注释位置贴近约束**：注释放在其解释的最小代码范围之前；只有 `noqa`、`type: ignore`、`pragma` 等短指令可以保留在行尾，避免把同一约束分散到远离实现的位置。
- **领域术语保持一致**：注释和 docstring 使用项目已经确定的领域词汇，例如 run、turn、session、checkpoint、tool call、provider 和 terminal event，不为同一概念随意创造近义名称。
- **名称服从领域语义**：同一概念在 Engine、会话、工具和前端之间使用同一名称；不得为了局部方便创建含义重叠但边界不同的近义名称。
- **指令注释必须局部说明原因**：`type: ignore`、`noqa`、`pragma` 和覆盖率排除只能放在无法用正常建模表达的精确位置，并用英文说明原因；不得用文件级关闭掩盖设计、类型或测试问题。
- **未决事项进入任务文档**：源码中不保留缺少负责人、背景和移除条件的 TODO/FIXME；未完成工作写入当前计划或任务卡，代码保持对当前行为的完整表达。
- **注释修整不得改变行为**：只整理注释和 docstring 的任务不得同时修改标识符、产品文本、异常文本、协议值、公共导出、控制流或数据结构；验收时应比较去除 docstring 后的可执行 AST，证明改动前后可执行代码等价。
- **自动格式保持统一**：Python 代码以项目锁定的 Ruff 检查和格式化结果为准，不为个人排版偏好引入例外。

## 5. 测试规范

这一部分解决的不是“要不要测试”，而是“哪些行为值得由哪一层测试保护，以及旧测试什么时候应该
被替换”。

- **测试保护稳定行为**：测试应说明产品契约、业务状态转换、安全边界或高风险算法，不为普通赋值、私有调用顺序和第三方库已经保证的行为堆积断言。
- **测试规模服从风险**：测试数量由失败影响、分支复杂度、兼容价值和真实环境风险决定，不追求覆盖每一行，也不以测试代码和产品代码的比例作为质量目标。
- **测试选择最低有效层**：纯校验放在单元测试，单模块状态转换放在组件测试，跨模块时序放在少量集成测试，安装和平台行为放在分发或真实环境验收；同一事实不在所有层重复证明。
- **公共行为优先**：能够通过返回值、公共事件、持久化结果或物理输出验证的行为，不直接读取或修改产品私有字段；只有无法从外部证明的重要内部不变量才允许专门的内部测试。
- **语义替换同步删改**：产品行为或实现契约被替换时，必须同步修改、合并或删除旧测试；不得为每次返工永久追加一组表达相同事实的新测试。
- **测试名称描述行为**：测试文件和函数名称说明被保护的领域行为与条件，不以阶段号、任务号、缺陷编号或施工顺序作为长期分类。
- **新测试就近归位**：新测试优先放入最接近被测行为边界的现有测试文件；只有独立契约或测试装配确有需要时才新建文件，新文件按行为命名。
- **共享夹具保持窄小**：重复的 Provider、App 和事件收集代码可以抽成共享 fake/harness，但共享夹具只封装稳定协议和必要构造，不隐藏大量默认状态或建立万能测试框架。
- **异步测试等待事实**：异步、并发和进程测试通过 Event、队列、状态变化或有界 `wait_for` 等可观察信号推进，并设置有余量的超时；只有验证时间行为、平台进程行为或证明延迟副作用没有发生时，才使用必要的墙钟等待，不用固定 sleep 猜测任务已经完成。
- **间歇失败先定位**：测试间歇失败时先保留诊断证据并定位原因，不用重复运行、放宽超时或跳过测试掩盖；只有发现不稳定性证据后才安排重复运行。
- **Mock 只隔离边界**：Mock、fake 和 monkeypatch 用于隔离网络、文件、时间、终端和进程等外部边界，不应把被测业务流程本身模拟掉；产品代码不内置 FakeProvider 等测试替身，Provider 协议测试在传输边界提供固定响应。
- **兼容样本真实**：持久化兼容和迁移测试使用真实旧格式的固定样本，不通过改写新 serializer 的版本号等方式伪造旧数据。
- **真实证据单独声明**：安装包、Windows Terminal、真实 Provider、进程树和文件系统平台行为需要独立验收；模拟测试通过不能表述为真实环境已经通过。
- **安全回归不可随意删除**：兼容迁移、路径越界、凭据清洗、权限绕过、取消清理和损坏数据等负向测试只有在等价保护已迁移或风险已消失时才能删除。
- **删除测试需要证明**：删除前说明该测试原本保护的行为、当前由哪里覆盖或为何不再成立；仅凭文件旧、数量多或运行慢不能删除。

## 6. Code review 与变更验收

- **审查先看系统位置**：review 先确认改动位于正确模块、状态所有者和依赖方向，再检查局部代码是否简洁；局部写法漂亮不能抵消错误的架构位置。
- **新增状态必须说明主人**：新增字段、缓存、队列、callback 或中间容器时，必须说明谁创建、谁修改、谁读取、何时结束，以及为何不能复用现有事实源。
- **新增抽象必须说明价值**：新增类、协议、adapter 或 helper 时，必须说明它隔离的变化原因和依赖；只被一次调用且没有独立语义的薄包装应保持内联。
- **新增依赖必须先查现状**：引入第三方依赖前先确认标准库和现有依赖不能满足需求，并评估安装、分发、维护和安全成本。
- **跨层改动必须同步检查**：公共契约或产品路径变化时，同时检查生产者、消费者、持久化、前端、测试、公共导出和事实文档，不能只修当前失败点。
- **验证范围匹配影响**：按 §6.1 选择与改动影响相符的验证范围；最终报告必须区分静态检查、自动化测试、构建和真实环境验收。
- **完成意味着没有双轨**：新实现只有在调用方完成迁移、旧路径删除、测试与文档同步后才算完成；保留未使用旧实现等待以后清理不属于完整交付。

### 6.1 验证矩阵

先完成可运行的功能闭环，再用代表性公共场景做聚焦验证；实现稳定后按下表补齐验证，不机械重复运行。
一次改动涉及多种类型时，取所有适用行的并集。

**基础检查**（所有代码或测试改动）：运行相关测试文件（`uv run pytest tests/<file>.py`），以及
`uv run ruff check src/mica_agent tests` 和 `uv run ruff format --check src/mica_agent tests`。

| 变更类型 | 在基础检查之上追加 |
|---|---|
| 仅文档 | 不需要基础检查；核对文中的路径、符号、命令和引用与实际文件一致 |
| 单模块内部实现，公共行为不变 | 无 |
| 跨模块契约、公共 API、事件顺序、取消语义或权限边界 | 全量 `uv run pytest`；涉及异步或资源生命周期时改用 `uv run pytest -W error` |
| 会话或配置的持久化格式 | 同上，并用真实旧格式固定样本验证兼容读取与迁移 |
| 依赖、入口或包资源 | 全量 `uv run pytest`，以及 `uv lock --check` 和 `uv build --offline` |
| 终端输入、渲染或视觉 | 全量 `uv run pytest`、虚拟终端物理帧回放，以及 `docs/assets/tui/README.md` 的视觉对照流程；最终由用户在真实 Windows Terminal 验收 |

真实 Provider、Windows Terminal、安装包和进程树等真实环境验收，与上表的自动化结论分开报告。

## 7. 必须触发设计审查的信号

出现以下任一情况时，执行者（worker 或单 agent）不应直接继续堆叠实现，而应先说明现状、目标边界和备选方案：

- 同一事实需要由两个对象共同更新；
- 为完成需求准备增加第二条实现路径或兼容分支；
- 核心模块需要导入具体前端、内置工具、Provider 或存储实现；
- 需要跨模块导入下划线私有符号；
- 准备新增 callback、sink、全局容器或共享可变字典传递状态；
- 一个函数开始同时推进多个生命周期或维护多组无关状态；
- 需要捕获 `Exception`/`BaseException`，吞掉错误或加入自动重试；
- 需要用固定 sleep、放宽断言或跳过测试才能通过验证；
- 需要修改公共 API、持久化格式、事件顺序、取消语义或权限边界；
- 需要新增第三方依赖、后台线程、异步任务、子进程或新的平台特例；
- 准备删除大量代码或测试，但还不能说明其行为由哪里替代。

设计审查不是要求把任务暂停到所有细节都完美，而是要求在高成本决策进入代码前，把状态所有者、
依赖方向、兼容边界和验证方法说清楚。
