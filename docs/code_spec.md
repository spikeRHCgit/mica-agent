# Mica 代码规范

> **状态**：2026-10-02 经用户确认定稿（D-016）；后续根据实际开发证据修订，不因单次偶发问题追加规则。
>
> **文档职责**：按产品代码、测试与验证、注释三类工作提供编写和审查指导；不记录任务进度或施工历史。

> 本文主要约束新增和修改的代码，不授权整改任务范围外的既有实现。既有架构调整仍遵循 D-014，不因规范定稿而启动重构。产品方向见 `docs/PROJECT_PLAN.md`，代码定位见 `docs/module_map.md`，具体交互规格见对应领域文档。

> 执行时先读与任务相关的区块；正确性、安全和兼容优先于局部简洁与排版。规则不能代替对实际调用关系和运行结果的检查，也不以文件长度、代码比例或测试数量单独判断质量。

## 1. 产品代码编写

目标：把功能放在正确位置，完成成功、失败和取消的完整处理，而不是只修好眼前的局部现象。

### 1.1 实现前：确定改动位置

- **先定位再实现**：确认用户入口、实际处理模块及受影响的调用方；涉及会话或界面时再追踪保存和展示路径，不只在最先发现问题的文件中追加补丁。
- **沿用已有职责**：已有模块负责目标行为时优先扩充其能力；新增模块或抽象前，说明现有能力为何不足，不为一次调用或假设中的未来需求增加薄包装。
- **明确状态归属**：新增状态、缓存或队列时，确定谁修改、谁读取、何时结束；展示副本和缓存从业务事实派生，不让多个对象分别维护同一判断。
- **保持依赖边界**：核心逻辑通过项目契约使用 Provider、工具、存储和前端能力；新增扩展沿用对应注册入口，不绕过权限与校验。需要跨模块复用私有符号时，先明确内部接口，不顺手扩大顶层公共 API。

### 1.2 实现中：保持清晰和可靠

**正确性与安全要求**

- **校验放在入口**：外部输入在对应 CLI、Provider、工具、文件或持久化边界校验后再进入内部流程；同一种解析、清洗和转换复用已有入口，不在每个消费者中各写一套。
- **业务事实不由界面重定义**：CLI/TUI 负责输入与显示，不自行生成工具结果、权限结论或运行终态；会话保存标准、可验证的数据，不保存 Provider 私有对象或界面组件。
- **资源必须明确收口**：任务、文件、客户端、终端模式和子进程有明确的资源所有者，由其处理正常、失败和取消后的释放；创建者默认负责，转交所有权时明确接收者，不能让多个对象都负责清理。
- **取消与终态保持一致**：沿用既有取消和中断保存契约，不吞掉 `CancelledError` 或把取消当作未知失败；每次运行、调用或交互只提交和发送一次终态，不在退出时留下未收口资源。
- **错误在边界处理**：只有能提供明确错误语义、清理资源或保护敏感信息的地方才捕获异常；不得静默吞错。诊断与持久化沿用既有清洗边界，凭据、本地绝对路径、未清洗工具参数和 Provider 原始响应不得直接进入对外错误、日志、repr 或工具展示。
- **旧数据仍可安全读取**：持久化格式改变时，明确版本、旧格式读取、迁移、原子写入和失败恢复；不把损坏数据宽松解析成有效记录，也不随意取消已承诺的兼容。

**代码组织要求**

- **按完整动作组织代码**：函数名称应能说明其主要动作；同时维护无关状态或承担独立职责时再拆分，不为缩短行数机械拆成大量小函数。
- **调用关系显式可读**：文件、网络、进程和保存等副作用放在职责清楚的接口中。回调或 sink 可以作为明确接缝，但要看得出调用方、数据方向和生命周期，不能靠共享可变容器隐藏业务流程。
- **名称与格式保持统一**：标识符使用含义明确的英文，沿用 run、turn、session、checkpoint 等既有概念；不为同一概念另造近义名称。检查和排版以项目 Ruff 配置为准。

### 1.3 交付前：核对关联影响

先审查改动位置、状态归属和失败路径，再检查局部写法。根据实际变化核对直接调用方、公共导出、
会话、界面和对应文档；未涉及的部分不做无目标的全仓检查。替换内部实现时一并迁移调用方和清理
旧路径，但保留仍有真实外部契约价值的兼容逻辑。验证范围按 §2.4 选择。

**需要先说明并确认的变化**：改变已确认的公共 API、持久化格式、事件顺序、取消语义或权限边界；
新增第三方依赖；改变模块职责或资源所有权，导致反向依赖、第二套业务状态或新的长期实现路径。
说明具体影响、可选方案和验证方式，按项目授权范围获得确认后再实现。

使用已有回调接口、已有执行路径中的异步任务或子进程，不单独构成暂停理由；不能因为出现某种
语法就要求重新设计。放宽断言、吞错或跳过失败也不是可接受的实现方案，先诊断失败原因。

## 2. 测试代码编写与验证

目标：用尽量少但有效的测试保护重要行为，及时维护已有资产；验证用于发现问题，不以测试数量
或反复全量运行作为工作量证明。

### 2.1 新增前：判断是否值得测试

- **先检查已有保护**：先找现有场景；能通过补充输入、关键断言或参数化表达的，不另建重复测试。新增测试要能说清失败时会损害哪项行为。
- **保护行为而非写法**：优先保护产品契约、状态转换、安全边界、兼容和容易出错的算法；不单独为普通赋值、私有调用顺序或第三方已经保证的行为堆积测试。
- **选择最低有效层**：纯校验和算法用单元测试，组件状态用组件测试，跨模块时序用少量集成测试；关键用户链路可另保留装配验证，但不同层要证明不同风险，不重复同一组事实。

### 2.2 编写时：让证据真实且确定

- **从可观察结果断言**：优先检查返回值、公共事件、保存结果或终端物理输出；确实无法从外部证明的重要内部约束，才专门访问私有实现。
- **替身只隔离边界**：fake、Mock 和 monkeypatch 用于网络、时间、终端等边界，不把目标业务流程本身模拟掉；共享 fixture 或 harness 只封装必要构造，不隐藏大量默认状态。
- **测试资源独立归属**：临时目录优先交给 pytest fixture 管理，业务替身只负责自身协议和资源；不把测试目录的清理职责塞进 Provider，不访问真实凭据、外部网络或真实用户会话目录。
- **等待实际完成信号**：并发测试用 Event、队列或状态通知确认目标操作已经完成，并设置有界等待；“已发送”不等于“已处理”。只有测试时间行为或确有平台观测需要时才保留墙钟等待，不用 sleep 猜测完成。
- **样本体现真实边界**：旧格式兼容使用真实旧格式固定样本，不靠修改新 serializer 的版本号伪造；不同取消入口、敏感输入和平台条件确有不同风险时，不因表面结果相同就合并掉。

### 2.3 维护时：避免重复与失效资产

- **按行为归档**：文件和函数按稳定行为命名，不使用阶段号或施工编号；新测试优先归入现有对应文件，独立契约或装配确有需要时再新建文件。
- **替换时同步删改**：行为改变或实现退役时同步更新旧测试，不为每次返工永久叠加相似场景。删除或合并前列明独有保护的去向；参数化测试核对具体输入项，不只核对函数名称或总数量。
- **保留关键负向保护**：路径越界、凭据清洗、权限绕过、取消清理、损坏数据和兼容迁移等测试，只有等价保护已经迁移或对应风险确已消失时才能删除；文件旧、运行慢和数量多不是删除理由。

### 2.4 验证安排：按影响选择，不机械重复

开发中先形成可运行的功能闭环，用代表性场景检查关键行为，发现问题后针对性验证；不要求每写一个
函数就增加单元测试或运行大套件。完整改动稳定后，按下表完成最终验收。任务验收可明确追加必要证据。

| 实际改动 | 最终验证 |
|---|---|
| 仅 Markdown 文档 | 核对事实、路径、章节和引用；不运行产品测试或构建 |
| 仅注释和 docstring | 按 §3.4 核对说明与行为等价，检查相关文件 Ruff；涉及对外说明时选择必要的公共入口检查，不默认全量或构建 |
| 局部实现或测试补强 | 运行受影响的测试与直接相关场景，检查修改文件 Ruff；不默认全量 |
| 公共行为、跨模块时序、权限、取消或核心装配改变 | 相关链路验证及最终全量；格式变化另验证真实旧数据读取、迁移和写入失败恢复 |
| 测试删除、合并或共享装配变化 | 核对原保护与最终收集项，运行受影响套件；影响多个行为域或全仓测试装配时补全量 |
| 依赖、安装入口、打包规则或包资源实际改变 | 锁文件核对、离线构建及相关分发/安装验证；同时改变运行行为或整体装配时补全量 |
| 终端输入、渲染或视觉实际改变 | 相关自动化、物理输出回放和用户真实 Windows Terminal 验收；视觉变化使用领域对照流程，共享输入/重绘机制改变时补全量 |

自动化测试使用 `uv run pytest <范围> -q -W error`；静态检查使用 `uv run ruff check <范围>`
和 `uv run ruff format --check <范围>`。需要时使用 `uv lock --check`、
`uv build --offline`，视觉流程见 `docs/assets/tui/README.md`。范围按实际行为影响判断，
不因改了某个入口文件的说明就自动选择入口行为变更的验证级别。

- **最终验证不机械重跑**：同一最终版本和环境的有效证据可以复用；再次修改后只补受影响的验证。需要全量时在稳定版本集中运行，不在每次局部修正后重复全量。
- **失败后保留现场**：失败时先记录首个错误、运行范围和环境，针对性诊断；有限重现或稳定性检查要有明确目的，不用反复运行直到通过。后续通过不代表历史间歇问题已经修复。
- **区分证据与结论**：静态检查、自动化、构建、真实环境和远端同步分别报告；模拟通过不能代替真实终端、Provider 或平台进程验收，未执行的验证明确说明。

## 3. 注释与 docstring 编写

目标：留下维护者无法直接从代码看出的原因和约束，不靠说明数量弥补代码可读性。

### 3.1 语言与范围

产品源码 `src/**` 的注释和正式 docstring 使用简洁英文；测试 `tests/**` 的说明性注释和正式
docstring 使用简洁中文；项目 Markdown 文档使用中文。标识符、命令、协议名和异常类型保留原形。
界面文本、错误消息、日志、提示词和测试样本不是说明性注释，不为语言统一而翻译。机器指令语法不变，
确需说明原因时使用所在目录的语言。

### 3.2 何时写、写什么

- **只补非显然信息**：说明设计原因、必须保持的约束、外部限制、兼容、安全以及取消和清理语义；不复述赋值、循环和函数名，也不为简单私有函数强制补 docstring。
- **说明与职责相符**：模块和类概括当前角色；公共入口说明调用者需要知道的输入、结果、失败和限制，不把每个符号都套进同一长模板。包介绍应覆盖真实导出范围，不写与实际实现相反的笼统结论。
- **不记录施工历史**：阶段号、任务号、worker、返工过程和未批准计划放任务或历史文档，不留在产品或测试说明中；真实的协议版本和平台限制可以保留。
- **同步维护准确性**：实现改变时检查附近说明是否仍然成立；未决事项放任务文档，需要暂留约束时说明原因与解除条件，不留无上下文的 TODO/FIXME。

### 3.3 放在哪里、怎样排版

- **贴近被解释的代码**：局部说明放在对应最小代码范围之前，模块、类和函数介绍使用正式 docstring；不把属性说明写成类体中的孤立字符串，不加无意义分区装饰。
- **保持短而一致**：使用既有领域词汇，保留正常多行 docstring 排版；重复说明合并，不强行把长段压成一行。行尾仅保留必要的 `noqa`、`type: ignore`、`pragma` 等指令，禁止用大范围关闭替代正常修复。

### 3.4 仅整理注释时的验收

注释专项不同时修改标识符、普通字符串、公共导出、断言、参数或执行流程。批量整理时比较剔除正式
docstring 后的可执行 AST，并检查机器指令及其附着代码不变；测试说明整理还要核对测试定义和参数
未变，涉及迁移时再核对完整收集项。AST 比较不覆盖说明真实性，也不能替代对普通字符串和指令的核对。
单处说明修正可直接审查精确 diff，不为它建立新的永久审计工具或测试。
