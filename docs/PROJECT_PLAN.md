## 1. 项目定位

Mica 是面向个人开发者的轻量 Agent 基座。它通过可靠的模型调用、工具执行、权限控制、会话管理
和终端交互形成完整的 Agent 工作闭环，并允许开发者通过稳定契约扩展工具、Provider、命令、
Skill、MCP 和事件能力。

核心价值：

- **轻量**：核心只保留通用 Agent 闭环必需的能力；
- **清晰**：状态、数据、职责和事实来源具有明确归属；
- **安全**：有副作用的工具调用必须经过统一校验和权限边界；
- **可靠**：完成、等待、失败、取消、持久化和恢复具有明确语义；
- **可扩展**：新增能力通过公开契约和显式注册接入，不修改 Agent Loop；
- **可部署**：Windows 用户可以通过简洁命令安装，并在任意工作区启动。

正式技术标识：

| 用途 | 标识 |
|---|---|
| 产品与仓库 | `Mica` / `mica` |
| 终端命令 | `mica` |
| npm 与 PyPI 分发包 | `mica-agent` |
| Python 导入包与源码目录 | `mica_agent` / `src/mica_agent/` |
| 全局用户目录 | `~/.mica/` |
| 全局配置 | `~/.mica/config.json` |
| 项目配置 | `<workspace>/.mica/config.json` |

## 2. 项目目标

Mica 的核心目标是形成以下完整闭环：

1. 用户通过终端界面提交指令并持续参与运行过程；
2. Agent Engine 使用当前模型推进推理、回复和多步工具调用；
3. 工具调用经过统一定义、参数校验、权限判断、执行和结果回传；
4. 一轮运行能够以完成、失败、取消或限制等明确状态结束，并在中断后保留真实进度；
5. 会话、配置和用户选择可以可靠保存、恢复和调整；
6. 工具、Provider、命令和外部能力可以在不侵入核心循环的前提下扩展；
7. 产品可以通过一致的自动化验证和真实环境验收进行维护与发布。

项目同时承担工程学习目标：所有阶段都应形成可运行、可验证的闭环，使架构选择、实现原因和权衡
可以从真实代码中被理解。

## 3. 产品范围

### 3.1 预期实现的核心功能范围

- Windows 优先的命令行与终端交互体验；
- 供应商无关的 Agent Loop、标准消息、结构化事件和统一取消；
- OpenAI-compatible Provider 连接，以及当前连接下的模型发现与切换；
- 原生 Tool Calling、流式响应、有限网络重试和多步工具循环；
- `read`、`write`、`edit`、`bash`、`ask` 五个内置工具；
- 所有工具共享的注册、校验、权限、执行、取消、输出限制和结果契约；
- `default` 与 `solo` 两种权限模式；
- 全局、项目、环境变量、命令行和会话级配置；
- 工作区隔离的会话持久化、恢复、分支、回退、清理与上下文管理；
- 终端命令、快捷键、状态信息和必要的交互选择界面；
- 全局与工作区 `AGENTS.md` 的启动上下文装配；
- 工具、Provider、命令、事件、Skill 和 MCP 适配所需的显式扩展契约；
- Python 核心与 npm 启动器配套的安装和分发能力。

### 3.2 明确非当前实现目标

- 多用户、多租户和服务端账号系统；
- 多 Provider 同时路由、自动模型切换和自动故障转移；
- Goal Mode、自治调度、定时任务和多 Agent 编排；
- 内置浏览器控制、计算机控制、网页清洗或通讯平台前端；
- Web、桌面端和聊天平台等多套内置界面；
- 复杂长期记忆、分层记忆和自动知识固化系统；
- 通过普通 XML 或 JSON 文本模拟原生 Tool Calling；
- 绕过工具注册、参数校验或权限系统的扩展执行路径；
- 历史项目的配置、会话、日志、命令、插件或 Python API 兼容层；
- 在核心中并列维护多个供应商的私有协议实现。

### 3.3 候选扩展

- MCP Client、远程工具和 Skill 的发现、选择与加载；
- 图片、文件等多模态输入；
- 浏览器、通讯平台、ACP 和可观测性集成；
- 费用统计、Prompt Cache 和更多 Provider 协议；
- `0.1.0` 发布后更完整的跨平台终端与 Bash 发现（非标准安装路径、显式路径配置、启动时可用性
  检查、缺失 Bash 时的友好降级）；公开工具名称仍固定为 `bash`，不以其他 shell 冒充；
- 操作系统级执行沙箱和网络隔离。

候选扩展不属于当前核心承诺，不得成为核心启动、安装或测试的必要依赖。任何候选能力只有在
明确进入阶段计划后，才转化为正式施工范围。

## 4. 技术基线与架构约束

本节是所有阶段计划和代码都必须满足的项目级约束。

### 4.1 技术基线

- **语言与并发**：
  - Python 最低版本为 3.11，不设置无必要的最高版本上限；
  - `asyncio` 是 Engine、Provider、工具等待和取消的统一并发模型，阻塞代码只在边界适配。
- **网络**：`httpx` 是唯一的 HTTP 客户端，不并存 `requests`、`aiohttp` 等第二套核心网络链路。
- **终端**：
  - 默认前端使用主缓冲区上的轻量保留式渲染（D-004）：终端拥有背景、scrollback 和鼠标滚动，
    Mica 只差分重绘自己的语义文档与底部交互区；
  - 外层 CLI 参数使用标准库 `argparse`。
- **工具链**：环境与构建使用 uv，自动测试使用 pytest，格式与静态检查使用 Ruff。
- **分发**：npm 只负责全局启动器、版本和安装分发，Agent 核心保持 Python 实现。

### 4.2 架构约束

- **运行模型**：
  - 一次用户指令对应一个 Run；一次模型请求及随后的工具处理对应一个 Turn；
  - 等待用户输入或权限确认是可恢复状态，不是 Run 结束；
  - 一次 Run 只以完成、失败、取消或限制中的一种终态结束。
- **工具入口唯一**：ToolSpec 是工具定义的唯一来源，ToolExecutor 是执行工具的唯一入口；参数与
  运行有效性校验先于权限策略。
- **权限不可绕过**：
  - 权限判断只消费规范化的工具事实，不修改原始执行参数；
  - 模型、提示词、AGENTS、工具输出和扩展都不能改变权限模式或批准请求；
  - 权限规则只防误操作，不构成执行沙箱。
- **单一 Provider 协议**：
  - 核心只交付 OpenAI-compatible Provider；其他协议通过独立 Provider 模块或扩展增加，不要求
    修改 Agent Engine；
  - 重试只发生在网络请求边界，不重复已经产生副作用的工具执行。
- **扩展只走注册面**：扩展只在应用装配阶段通过公开注册面接入（Phase 8），不修改 Agent Loop。
- **启动上下文冻结**：
  - 内置系统提示词与 AGENTS 在会话激活时读取并组装一次，之后在该会话内保持不变；
  - AGENTS 只提供上下文和行为说明，不能修改权限、扩大工作区边界或自动批准工具。
- **本地数据分离**：
  - 用户数据位于 `~/.mica/`；
  - 日志、会话、缓存、扩展和专用运行环境使用独立目录，会话按工作区隔离；
  - 调试日志不能充当会话存储或恢复来源。
- **独立实现**：`src/mica_agent/` 是唯一的产品源码；引入的任何第三方代码都必须履行其许可证
  要求。

### 5.3 Phase 6 需求简报：配置与模型

**已确认**

- **配置来源**：
  - 优先级为：当前会话 > CLI 参数 > 环境变量 > 项目配置 > 全局配置 > 程序默认值；
  - 覆盖关系显式、可解释，不由业务模块私自读取多套来源。
- **配置文件**（路径见 §1）：
  - 使用简单 JSON 键值；
  - 不把内置权限矩阵复制进配置文件，也不把环境变量反写入配置文件。
- **API Key**：
  - 可以保存在受限权限的全局用户配置中，也可以由环境变量覆盖；
  - 项目配置不默认写入明文 API Key，手工写入时必须提示泄露风险。
- **连接与模型分离**：连接配置与模型信息是两个契约；切换模型只替换模型信息，不修改标准会话历史。
- **首次启动向导**：
  - 引导填写 API URL 和 API Key，执行连接测试并选择默认模型；
  - 连接失败时可以保存并进入界面，但对话保持不可用提示，直到验证成功。
- **会话默认值**：新会话从用户配置读取默认思考强度、工作模式和权限模式；会话内修改默认只影响
  当前会话。
- **工作模式与权限模式**：工作模式决定直接执行还是先规划，权限模式决定工具允许、询问或拒绝；
  两者互不隐式修改。
- **`/model`**：
  - 实时探测当前 Provider 的模型 ID 和最大上下文；探测失败时允许手动输入模型 ID；
  - 上下文上限未知时使用可覆盖的 200K 默认值，并明确标记为默认值；
  - 切换到上下文更小的模型时先警告并确认；用户坚持后允许切换，不静默裁剪历史。
- **`Shift+Tab`**：在两种权限模式间切换；运行中只记录待生效值，当前循环结束后提交，不修改已
  冻结的系统提示词。
- **选择类弹窗**：在模型、配置等选择弹窗中，单击 `Esc` 只关闭弹窗；Ask 与权限面板中的 `Esc`
  仍按 `docs/tui_design.md` §6.5 取消当前 Run。

**倾向**

- 斜杠命令的基础机制随 `/model`、`/config` 在本阶段建立。

**留给阶段计划**

- 配置字段、校验与版本迁移；
- 向导的交互形式；模型探测使用的接口；
- 工作模式中「先规划」的具体行为与呈现；
- 设置界面（`docs/tui_design.md` §13 第 1 项），以及权限模式在事实区的显示位置（同文 §4.1）；
- 界面偏好的范围；
- 代码结构、任务拆分与验证方式。

- **依赖**：阶段间治理完成。
- **对应项目验收**：§6「配置与模型」。

### 5.4 Phase 7 需求简报：会话命令与上下文

**已确认**

- **命令清单**：
  - 核心斜杠命令为 `/help`、`/new`、`/rename`、`/branch`、`/rewind`、`/clear`、`/btw`、`/model`、
    `/config`、`/compact`（`/model`、`/config` 属于 Phase 6）；
  - 不提供会话内 `/resume`、`/sessions`、`/switch`、`/quit`、`/stop`、`/status`、`/cost`、
    `/export` 或 `/permissions`。
- **基础会话命令**：`/new` 创建新会话；`/rename` 设置标题；`/branch` 复制当前完整会话。
- **`/rewind`**：
  - 打开历史选择界面，删除所选用户指令及其后的会话内容，不回滚工作区文件；
  - 空闲时双击 `Esc` 打开 `/rewind`。
- **`/clear`**：保留当前会话身份、标题和配置，清空全部内容。
- **`/btw`**：使用主会话的只读上下文执行一次旁路请求；结果不写入主会话，也不能继续追问。
- **`/compact`**：
  - 支持主动触发和上下文阈值触发；
  - 采用非破坏性记录：原始 TurnEntry 保持不变，压缩结果作为覆盖指定历史范围的记录追加保存；
  - 模型上下文使用最新的有效压缩记录及其后的 TurnEntry。
- **压缩与其他命令的关系**：
  - 自动压缩只在当前 Run 结束后的安全边界执行；
  - `/branch` 复制压缩记录；`/clear` 清除全部记录；`/rewind` 同时移除失效的压缩记录。
- **写入安全**：更新、清空和回退会话时不得产生部分写入或损坏原文件。
- **事实区**：上下文用量等字段只有在存在稳定事实源并完成独立设计后才显示。

**倾向**

- `/help` 与完整快捷键帮助界面（`docs/tui_design.md` §13 第 2 项）在本阶段交付。

**留给阶段计划**

- 会话选择界面的入口与形式；
- 摘要算法、提示词、token 预算、阈值、失败重试和具体 JSONL 字段，这些允许在后续版本迭代优化；
- 会话格式升级与迁移，以及中断检查点与 `/rewind`、`/branch`、`/compact` 的关系；
- 恢复会话时重建长粘贴摘要（`docs/tui_design.md` §13 第 3 项）是否随格式升级一起完成；
- Phase 3 已交付的会话服务能力与本阶段命令之间的差距；
- 代码结构、任务拆分与验证方式。

- **依赖**：Phase 6（命令机制；压缩阈值来自配置）。
- **对应项目验收**：§6「会话与恢复」。

### 5.5 Phase 8 需求简报：扩展契约

**已确认**

- **接入方式**：扩展只在应用装配阶段通过 ExtensionAPI 提供能力：

  ```text
  Extension / MCP Adapter / Skill Loader
      -> ExtensionAPI
         -> Tool / Provider / Command Registries、Event Bus
  ```

- **核心交付物**：ExtensionAPI、扩展发现与加载、稳定注册契约、扩展权限声明、开发文档，以及一个
  最小工具扩展示例。
- **发现与可见范围**：
  - 扩展通过显式入口点发现，不依靠 monkey patch、导入副作用或私有字段访问；
  - ExtensionAPI 只暴露公开注册面，不暴露内部对象。
- **边界**：扩展不能修改 Engine 私有状态，也不能绕过工具注册、参数校验或权限策略。
- **MCP 与 Skill**：
  - MCP 工具必须转换为普通 ToolSpec；
  - Skill 是上下文与流程资源包，不能绕过工具和权限系统执行代码；
  - MCP Client 与 Skill 加载实现作为后续独立扩展交付，不进入核心安装路径。

**留给阶段计划**

- 注册面的具体形状、入口点名称和扩展权限声明格式；
- 扩展工具在终端中的专用展示方式；
- 公共 API 分层与治理期 code spec 决定的衔接；
- 代码结构、任务拆分与验证方式。

- **依赖**：阶段间治理对公共 API 分层的决定（`docs/code_review_report.md` §12 第 2 项）。
- **对应项目验收**：§6「扩展能力」「安全边界」。

## 6. 项目级验收标准

Mica 的 `0.1.0` 需要同时满足以下条件：

- **核心闭环**：可以通过真实 Provider 稳定完成多轮模型、工具和用户交互；
- **终端体验**：主要终端入口使用一致的应用服务和事件契约，关键交互在 Windows 真实终端通过验收；
- **工具与权限**：内置工具经过统一校验、权限、取消、输出限制和结构化结果处理；
- **会话与恢复**：成功、失败和中断进度可以安全保存，主要会话操作不破坏已有数据；
- **配置与模型**：配置来源、模型发现、切换、上下文限制和有限重试具有明确、可解释的行为；
- **扩展能力**：新增工具、Provider 或命令不需要修改 Agent Engine 的核心循环；
- **安全边界**：模型、提示词、AGENTS 和扩展不能自行提升权限或绕过工具执行边界；
- **自动验证**：默认测试不依赖真实 Key、外部网络或随机模型输出，真实集成验收独立执行；
- **安装分发**：Windows 用户可以从任意工作区安装并启动，缺少前置条件时得到可操作的错误；
- **工程质量**：公开契约、代码规范、模块职责和文档事实源保持一致，项目不存在并行的废弃实现；
- **发布一致性**：产品名、命令、包、版本、许可证和公开文档在正式发布前统一收口。

阶段完成只代表其阶段计划中的验收已经通过，不自动等同于 `0.1.0` 产品验收完成。
