# Mica 项目总计划

> 由 master 维护，只写跨阶段都成立的内容。
> 当前进度在 `docs/STATUS.md`。

## 定位与目标

- 用途：轻量的 Agent 基座。通过可靠的模型调用、工具执行、权限控制、会话管理和终端交互形成完整的 Agent 工作闭环，并允许通过稳定契约扩展工具、Provider、命令、Skill、MCP 和事件能力。
- 用户：个人开发者，在 Windows 终端里从任意工作区启动使用。
- 目标：
  - 形成完整闭环：
    1. 用户通过终端界面提交指令，并持续参与运行过程；
    2. Agent Engine 使用当前模型推进推理、回复和多步工具调用；
    3. 工具调用经过统一定义、参数校验、权限判断、执行和结果回传；
    4. 一轮运行以完成、失败、取消或限制等明确状态结束，中断后保留真实进度；
    5. 会话、配置和用户选择可以可靠保存、恢复和调整；
    6. 工具、Provider、命令和外部能力可以在不侵入核心循环的前提下扩展；
    7. 产品可以通过一致的自动化验证和真实环境验收进行维护与发布。
  - 产品要求：
    - **轻量**：核心只保留通用 Agent 闭环必需的能力；
    - **清晰**：状态、数据、职责和事实来源有明确归属；
    - **安全**：有副作用的工具调用必须经过统一校验和权限边界；
    - **可靠**：完成、等待、失败、取消、持久化和恢复有明确语义；
    - **可扩展**：新增能力通过公开契约和显式注册接入，不修改 Agent Loop；
    - **可部署**：Windows 用户可以通过简洁命令安装，并在任意工作区启动。
  - 工程学习：每个阶段都形成可运行、可验证的闭环，架构选择、实现原因和权衡能从真实代码中理解。

## 各阶段需求简报

### 阶段 7：会话命令与上下文

- 子阶段目标：
  用户能在会话内新建、命名、分支、回退、清空会话，发起不写入主会话的旁路请求，并在上下文变长时主动或自动压缩。

- 具体实现范围：
  - 会话选择界面；
  - 会话命令 `/new`、`/rename`、`/branch`、`/rewind`、`/clear`、`/btw`；
  - `/compact` 上下文压缩，主动触发和阈值触发；
  - 上下文用量显示。

- 已确认：
  - 核心斜杠命令为 `/help`、`/new`、`/rename`、`/branch`、`/rewind`、`/clear`、`/btw`、`/model`、`/settings`、`/compact`；`/login`、`/model`、`/settings`、`/reload` 属于阶段 6。不提供会话内 `/resume`、`/sessions`、`/switch`、`/quit`、`/stop`、`/status`、`/cost`、`/export` 或 `/permissions`。
  - `/new` 创建新会话；`/rename` 设置标题；`/branch` 复制当前完整会话。
  - `/rewind` 打开历史选择界面，删除所选用户指令及其后的会话内容，不回滚工作区文件；空闲时双击 `Esc` 打开。
  - `/clear` 保留当前会话身份、标题和配置，清空全部内容。
  - `/btw` 使用主会话的只读上下文执行一次旁路请求；结果不写入主会话，也不能继续追问。
  - `/compact` 采用非破坏性记录：原始 TurnEntry 保持不变，压缩结果作为覆盖指定历史范围的记录追加保存；模型上下文使用最新的有效压缩记录及其后的 TurnEntry。
  - 自动压缩只在当前 Run 结束后的安全边界执行；`/branch` 复制压缩记录，`/clear` 清除全部记录，`/rewind` 同时移除失效的压缩记录。
  - 更新、清空和回退会话时不得产生部分写入或损坏原文件。
  - 上下文用量等事实区字段，只有在存在稳定事实源并完成独立设计后才显示。
  - 依赖阶段 6：命令机制沿用阶段 6 的统一命令入口（D-023），压缩阈值来自配置。
- 倾向：
  - `/help` 与完整快捷键帮助界面（`docs/tui_design.md` §13 第 2 项）在本阶段交付。
- 留给子阶段计划的正式讨论阶段：
  - 会话选择界面的入口与形式；
  - 摘要算法、提示词、token 预算、阈值、失败重试和具体 JSONL 字段，允许在后续版本迭代优化；
  - 会话格式升级与迁移，以及中断检查点与 `/rewind`、`/branch`、`/compact` 的关系；
  - 恢复会话时重建长粘贴摘要（`docs/tui_design.md` §13 第 3 项）是否随格式升级一起完成；
  - 阶段 3 已交付的会话服务能力与本阶段命令之间的差距。

### 阶段 8：扩展契约

- 子阶段目标：
  开发者不修改 Agent Engine，就能通过公开注册面接入新的工具、Provider、命令和事件处理。

- 具体实现范围：
  - ExtensionAPI 与稳定注册契约；
  - 扩展的显式发现与加载；
  - 扩展权限声明；
  - 扩展开发文档和一个最小工具扩展示例。

- 已确认：
  - 扩展只在应用装配阶段通过 ExtensionAPI 提供能力：Extension / MCP Adapter / Skill Loader → ExtensionAPI → Tool / Provider / Command Registries、Event Bus。
  - 扩展通过显式入口点发现，不依靠 monkey patch、导入副作用或私有字段访问；ExtensionAPI 只暴露公开注册面，不暴露内部对象。
  - 扩展不能修改 Engine 私有状态，也不能绕过工具注册、参数校验或权限策略。
  - MCP 工具必须转换为普通 ToolSpec；Skill 是上下文与流程资源包，不能绕过工具和权限系统执行代码；MCP Client 与 Skill 加载实现作为后续独立扩展交付，不进入核心安装路径。
  - 新增扩展注册面的公开边界按 `docs/code_spec.md` §1.1、§1.3 确定；既有公共导出保持，整体分层重构按 D-014 延期，不作为本阶段的前置任务。
- 倾向：
  - 无。
- 留给子阶段计划的正式讨论阶段：
  - 注册面的具体形状、入口点名称和扩展权限声明格式；
  - 扩展工具在终端中的专用展示方式；
  - 公共 API 分层与 `docs/code_spec.md` 的衔接。

### 阶段 9：分发与 MVP 收口

- 子阶段目标：
  Windows 用户用一条 npm 命令安装 Mica 并在任意工作区启动，`0.1.0` 的版本、许可证和公开文档准备就绪。依赖阶段 6～8 完成、功能封顶。

- 具体实现范围：
  - npm 启动器与同版本 Python 核心的配套分发；
  - 专用 Python 环境的建立、升级与卸载；
  - 安装态系统验收；
  - 公开文档、许可证和 `0.1.0` 发布准备。

- 已确认：
  - Windows 是首要验收平台，同时避免无必要的平台绑定。
  - Node.js/npm 与 Python 或 uv 是外部前置环境；安装器不自动修改系统环境。
  - npm 包只承担启动器、版本和全局命令分发；首次运行时在 Mica 用户目录中建立专用 Python 环境，安装与 npm 包严格同版本的 Python 核心；npm 包与 Python wheel 同版本发布、升级和卸载，不无版本约束地拉取最新核心。
  - 初始公开版本号为 `0.1.0`；Git 标签、npm 包和 Python wheel 使用同一版本。
  - GitHub 仓库 `spikeRHCgit/mica-agent` 目前为私有（2026-10-04 按用户要求）；拟采用宽松的开源许可证。许可证名称、发布账号、签名和自动发布流程在 `0.1.0` 功能封顶时确认。
  - PowerShell 一行安装脚本是后续候选，不属于核心交付要求。
- 倾向：
  - 无。
- 留给子阶段计划的正式讨论阶段：
  - 启动器的实现方式；
  - 专用环境的位置、升级与卸载流程；
  - 安装态验收矩阵和公开文档范围。

## 产品范围

- 核心：
  - Windows 优先的命令行与终端交互体验；
  - 供应商无关的 Agent Loop、标准消息、结构化事件和统一取消；
  - 多供应商连接，独立的 Chat Completions、Responses、Anthropic Messages 适配，以及模型发现与切换；
  - 原生 Tool Calling、流式响应、有限网络重试和多步工具循环；
  - `read`、`write`、`edit`、`bash`、`ask` 五个内置工具（D-002）；
  - 所有工具共享的注册、校验、权限、执行、取消、输出限制和结果契约；
  - `default` 与 `solo` 两种权限模式（D-003）；
  - 全局、项目、环境变量、命令行和会话级配置；
  - 工作区隔离的会话持久化、恢复、分支、回退、清理与上下文管理；
  - 终端命令、快捷键、状态信息和必要的交互选择界面；
  - 全局与工作区 `AGENTS.md` 的启动上下文装配；
  - 工具、Provider、命令、事件、Skill 和 MCP 适配所需的显式扩展契约；
  - Python 核心与 npm 启动器配套的安装和分发能力。
- 候选扩展（不成为核心启动、安装或测试的必要依赖）：
  - MCP Client、远程工具和 Skill 的发现、选择与加载；
  - 图片、文件等多模态输入；
  - 浏览器、通讯平台、ACP 和可观测性集成；
  - 费用统计、Prompt Cache 和更多 Provider 协议；
  - `0.1.0` 发布后更完整的跨平台终端与 Bash 发现（非标准安装路径、显式路径配置、启动时可用性检查、缺失 Bash 时的友好降级）；公开工具名称仍固定为 `bash`，不以其他 shell 冒充；
  - 操作系统级执行沙箱和网络隔离。
- 不做：
  - 多用户、多租户和服务端账号系统；
  - 多 Provider 同时路由、自动模型切换和自动故障转移；
  - Goal Mode、自治调度、定时任务和多 Agent 编排；
  - 内置浏览器控制、计算机控制、网页清洗或通讯平台前端；
  - Web、桌面端和聊天平台等多套内置界面；
  - 复杂长期记忆、分层记忆和自动知识固化系统；
  - 通过普通 XML 或 JSON 文本模拟原生 Tool Calling；
  - 绕过工具注册、参数校验或权限系统的扩展执行路径；
  - 历史项目的配置、会话、日志、命令、插件或 Python API 兼容层；
  - 在核心中并列维护多个供应商的私有协议实现（D-017）。

## 架构

- 技术栈：
  - Python 3.11 起，不设无必要的最高版本上限；`asyncio` 是 Engine、Provider、工具等待和取消的统一并发模型，阻塞代码只在边界适配。
  - `httpx` 是唯一的 HTTP 客户端，不并存 `requests`、`aiohttp` 等第二套核心网络链路。
  - 终端默认使用主缓冲区上的轻量保留式渲染（D-004）：终端拥有背景、scrollback 和鼠标滚动，Mica 只差分重绘自己的语义文档与底部交互区；外层 CLI 参数使用标准库 `argparse`。
  - 环境与构建使用 uv，测试使用 pytest，格式与静态检查使用 Ruff。
  - npm 只负责全局启动器、版本和安装分发，Agent 核心保持 Python 实现。
  - 正式标识：产品与仓库 `Mica` / `mica`；终端命令 `mica`；npm 与 PyPI 分发包 `mica-agent`；Python 导入包与源码目录 `mica_agent` / `src/mica_agent/`；全局用户目录 `~/.mica/`；全局配置 `~/.mica/config.json`；项目配置 `<workspace>/.mica/config.json`。
- 总体结构：CLI 解析参数和配置后装配应用（App）；App 持有配置、会话和模型连接，每轮驱动唯一的 Agent Engine；Engine 通过 Provider 契约调用模型、通过 ToolExecutor 执行工具，并以有序事件把进度交给终端前端；会话按工作区保存为 JSONL。
- 核心子系统：
  - 应用与 CLI：命令行入口、应用装配、每轮运行和取消生命周期；
  - 配置：配置文件读取与保存、来源选择、模型能力和凭据保护；
  - 公共契约：消息、事件、工具、会话和校验的供应商无关数据结构；
  - 会话与工作区：工作区身份、AGENTS 上下文、JSONL 存储和会话业务；
  - 工具与权限：工具注册、校验、授权、执行和内置工具；
  - Provider 与 Engine：模型协议适配和单一 Agent Loop；
  - 终端前端：主缓冲区的输入、渲染、交互和运行控制。
- 边界：
  - 一次用户指令对应一个 Run；一次模型请求及随后的工具处理对应一个 Turn。等待用户输入或权限确认是可恢复状态，不是 Run 结束；一次 Run 只以完成、失败、取消或限制中的一种终态结束。
  - ToolSpec 是工具定义的唯一来源，ToolExecutor 是执行工具的唯一入口；参数与运行有效性校验先于权限策略。
  - 权限判断只消费规范化的工具事实，不修改原始执行参数；模型、提示词、AGENTS、工具输出和扩展都不能改变权限模式或批准请求；权限规则只防误操作，不构成执行沙箱。
  - 核心循环消费供应商无关契约；Chat Completions、Responses、Anthropic Messages 通过独立 Provider 模块适配，不在 Engine 内分叉成多套私有协议循环（D-017）。重试只发生在网络请求边界，不重复已经产生副作用的工具执行。
  - 扩展只在应用装配阶段通过公开注册面接入，不修改 Agent Loop。
  - 内置系统提示词与 AGENTS 在会话激活时读取并组装一次，之后在该会话内保持不变；AGENTS 只提供上下文和行为说明，不能修改权限、扩大工作区边界或自动批准工具。
  - 用户数据位于 `~/.mica/`；日志、会话、缓存、扩展和专用运行环境使用独立目录，会话按工作区隔离；调试日志不能充当会话存储或恢复来源。
  - `src/mica_agent/` 是唯一的产品源码；引入的任何第三方代码都必须履行其许可证要求。

## 项目级验收

`0.1.0` 需要同时满足以下条件；单个阶段通过验收，不等于项目验收完成。

- 核心闭环：可以通过真实 Provider 稳定完成多轮模型、工具和用户交互。
- 终端体验：主要终端入口使用一致的应用服务和事件契约，关键交互在 Windows 真实终端通过验收。
- 工具与权限：内置工具经过统一校验、权限、取消、输出限制和结构化结果处理。
- 会话与恢复：成功、失败和中断进度可以安全保存，主要会话操作不破坏已有数据。
- 配置与模型：配置来源、模型发现、切换、上下文限制和有限重试具有明确、可解释的行为。
- 扩展能力：新增工具、Provider 或命令不需要修改 Agent Engine 的核心循环。
- 安全边界：模型、提示词、AGENTS 和扩展不能自行提升权限或绕过工具执行边界。
- 自动验证：默认测试不依赖真实 Key、外部网络或随机模型输出，真实集成验收独立执行。
- 安装分发：Windows 用户可以从任意工作区安装并启动，缺少前置条件时得到可操作的错误。
- 工程质量：公开契约、代码规范、模块职责和文档事实源保持一致，项目不存在并行的废弃实现。
- 发布一致性：产品名、命令、包、版本、许可证和公开文档在正式发布前统一收口。
