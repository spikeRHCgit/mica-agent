
# 重构范围控制

- 用户所说的“一条命令部署”特指首期 Windows 环境中，在已安装 Python 或 uv 的前提下，一条终端命令完成安装并注册 `ga`；首次启动再通过交互向导配置供应商、API 地址、API Key 和模型。
- 用户所说的“高可扩展”特指代码层面的积木式扩展：新增工具、模型协议或前端适配器时应添加独立模块并注册，不应修改核心循环或在多个隐含位置重复登记。
- 第一阶段不建设复杂的多供应商路由和自动故障转移。只要求易于设置或更改当前供应商、在当前供应商下发现和切换模型、切换模型时保留标准化对话历史，以及当前模型请求失败时进行有限重试。
- 重构讨论预计跨越多轮；每轮确认的重要决策必须同步到 `docs/refactor_draft.md`，并区分已确认、工程约束和待讨论，避免上下文压缩造成决策漂移。
- 重构总原则是“快刀斩乱麻、化繁为简”。设计评审时优先删除臃肿功能和隐式耦合，防止用插件框架、抽象层或兼容逻辑制造超过当前目标的新复杂度。
- 新版 `config.json` 参考 Claude Code `settings.json`，优先使用少量、稳定、容易手工维护的键值；禁止把三种权限模式的完整规则或复杂安全边界复制进配置文件。
- 首次模型配置只收集稳定连接字段和一个默认模型；仅在用户执行 `/model` 时实时探测模型 ID 与最大上下文，无法获取上下文时首期使用可覆盖的 200K 默认值。
- “Don't Ask”的语义已经落实为 `solo mode`：除代码内置的危险操作和越界请求外，普通工具调用自动允许。
- 首期设计必须优先满足用户的“怎么简单怎么来”：不要为了未来可能出现的分支、回退或审计能力提前引入树形存储、leaf 指针或共享历史；当前已确认 `/rewind` 采用直接截断，未来增强必须另行讨论。
- 当状态信息需要频繁查看时，优先设计常驻、只读的状态栏；不要为同一信息继续增加 `/sessions`、`/resume`、`/switch` 等重复查询命令，除非命令承担了状态变更职责。
- 配置入口要区分会话临时设置和用户级默认配置：`/config` 面向当前会话，`ga config`/`config.json` 面向持久化默认值；权限模式切换使用用户快捷键，不再增加专用斜杠命令。
- 权限模式正式确定为 `default`、`accept_edits`、`solo mode`；内部值可用 `solo`，显示名称保留 `solo mode`。权限模式只控制已配置安全边界内的确认策略，不改变工作模式、思考强度或工具集合。
- 权限模式矩阵由项目代码中的内置策略表定义，不写入 `config.json`：`default` 默认只自动允许读取，`accept_edits` 额外自动允许创建/修改文件，`solo mode` 自动允许除危险操作外的普通工具调用。
- `permissions.allow` 参考 Claude Code，用于声明所有普通权限模式下都自动允许的工具或操作匹配规则；决策优先级是硬性拒绝 > `permissions.allow` > 当前模式，因此 allow 列表不能覆盖危险指令或系统级硬限制。
- `danger` 不进入首期实现，不进入 `Shift+Tab` 循环，也不提供命令入口；“不打扰我”不能等价于“获得系统全部权限”。
- `/config` 只接受无参数形式并打开弹出式设置界面；不增加 `/config set ...` 快速修改语法。设置面板与 `/model` 共用配置/模型选择服务，权限模式在面板中只读，避免出现重复入口和分叉逻辑。
- `default` 模式的确认授权只对当前一次工具调用有效，不缓存为当前任务或当前会话的同类授权。
- 权限检查必须放在统一的工具执行器/分发入口，而不是分散写在 `do_read`、`do_write`、`do_code_run` 等具体工具中；工具注册信息声明能力，PolicyEngine 根据工具声明、实际参数、当前模式和边界返回 `ALLOW`、`ASK` 或 `DENY`。
- 运行 Agent 循环时，`Shift+Tab` 只记录待生效模式；当前循环结束后才提交切换。会话结束时保存最后生效的权限模式，`--resume` 恢复该模式，新会话从 `config.json` 的默认模式开始。
- 重构讨论必须维护唯一、有顺序、有状态的队列；每轮只处理第一个待讨论项，确认后同步草案状态再推进，禁止同时在工具、会话、前端和部署之间无序跳转。
- 首期内置工具固定为简洁的 `read`、`write`、`edit`、`ls`、`bash`、`ask`。删除旧 `code_run` 的 `inline_eval`、回复代码块隐式执行、文件引用模板和 Handler 内部对象暴露；文本搜索首期通过 `bash` 完成，未来可作为 `grep` 扩展加入。
- 工具定义必须以单一 `ToolSpec` 同时承载名称、描述、参数、权限能力和处理器，并统一返回 `ToolResult`；Schema、帮助、参数校验和权限请求从注册信息生成，禁止在 JSON、Handler 和提示词中重复登记。
- 扩展必须使用显式 Python entry point 和 `setup(ExtensionAPI)` 注册，禁止 monkey patch、导入副作用和私有字段访问。Python 工具与 MCP 代理工具进入同一个 `ToolRegistry`；Skill 作为独立上下文包注册，不能绕过工具注册表和权限引擎执行代码。
- 架构讨论必须区分两类决策：用户确认产品体验、功能边界和价值取舍；Agent 负责提出并验证底层数据结构、状态机、并发和异常处理方案。解释底层机制是为了让用户理解取舍，不能把陌生技术名词包装成必须由用户逐项背书的选择题。
- 面向用户的历史操作不能暴露内部节点编号要求用户记忆。类似 `/rewind` 的定位应使用无参数命令打开可读选择界面，界面项携带内部稳定 ID；同时必须明确操作是否只影响会话，避免让用户误以为工作区文件也会回滚。
- 模型上下文不足时，先展示风险并请求用户确认，不把供应商报告的上下文上限当成绝对真理；未知上下文使用明确标注的默认值。模型探测失败时保留手动模型 ID 后备，避免把兼容接口的可选能力变成硬依赖。
- 首期安装遵循“应用安装”和“系统环境管理”分离：npm 只分发无交互启动器，首次运行只建立 `~/.ga/runtime/` 内的项目专用环境；Node.js/npm、Python 或 uv 缺失时给出可操作错误，不为追求一行命令提前维护系统级自动安装脚本。
- 跨多轮维护的重构草案只负责保存决策，允许按讨论顺序增量追加，不能直接作为实施规范。准备阶段结束后必须先把草案去重、重排并统一格式，形成用户单独验收的正式重构方案；正式方案未批准前不开始业务代码实现。
- Mica 正式重建采用 cAc：当前 Codex 作为 master 负责计划、契约、外部 Claude Code worker 派工、审查和文档收口，默认不亲自实现业务代码，也不以内置 subagent 替代用户所指的外部 worker。
- 用户提供的测试 API Key 只能通过本机环境变量或 Git 忽略配置注入；不得写入项目文档、任务单、日志、会话文件或提交。产品代码不实现 `FakeProvider`，自动化测试优先在 HTTP 传输边界提供固定响应，真实 Provider 调用作为独立集成验收。
- 重构准备阶段只确认会影响整个项目且后期难以低成本推翻的边界，不提前编写第一阶段交付切片、文件清单、类名、函数签名或具体测试用例。正式项目方案保持稳定但不过细；每个阶段开始前再按当时需求和源码制定阶段计划，为 vibe coding 保留调整空间。
- 每次提出新的确认问题前，必须先对照用户最新答复、`PROJECT_PLAN.md` 和历史决策记录检查该事项是否已经确认；已接受的方案要立即从开放问题中移除，禁止因状态同步遗漏要求用户重复确认。
- 当剩余项目级决策数量较少且彼此可以独立判断时，应一次性给出全部建议、影响和默认方案供用户集中确认；只有存在前后依赖或高风险分歧时才拆成多轮，避免机械地一项一轮拖慢推进。
- 项目计划只锁定会影响长期数据和模块边界的功能语义；摘要算法、阈值、提示词、具体持久化字段和发布操作等可变细节应留到对应构建阶段或版本封顶时确认，并允许后续迭代优化。
